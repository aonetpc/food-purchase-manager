### 1.1 背景

用户提了需求：
- 预订看板各业务行左侧当前显示"X 项"（当前 7 天的项目卡片数）

### 1.2 跨月显示策略

看板默认显示当前周（周一~周日 7 天），跨月时有 3 种情况。采用**取当前周里天数较多的那个月（主月）**的方案：

| 场景 | 示例 | 显示月份 |
|---|---|---|
| 周完全在一个月内 | 9/7~9/13 全在 9 月 | 9 月 |
| 周跨两个月（后半月） | 9/28~10/4：9月3天、10月4天 | 10 月 |
| 周跨两个月（前半月） | 10/26~11/1：10月4天、11月3天 | 10 月 |

**实现**（前端 `dominantMonth` useMemo）：
```js
const monthCounts = {};
weekDates.forEach(d => {
  const m = `${d.getFullYear()}-${String(d.getMonth() + 1).padStart(2, '0')}`;
  monthCounts[m] = (monthCounts[m] || 0) + 1;
});
return Object.entries(monthCounts).sort((a, b) => b[1] - a[1])[0][0];
```

**日期格式**：不显示年份，只显示"9月: 120人"。

### 1.4 Bug 发现：人数明细不对

部署后用户反馈：体检/早餐/中餐/晚餐的月度人数全部不对。

### 1.5 根因分析

| 业务 | 数据库 pax 存储 | 纯 SQL 查询结果 | 实际人数 |
|---|---|---|---|
| **早餐** | **不在 booking_items 表**——是派生项（`deriveBreakfastItems` 在读取订单时动态生成，不在表里） | `SUM(pax)=0`（表里没有 breakfast 行） | 400+ 人 |
| **午餐** | 按桌模式存 `tables`（如 4），按人模式存 `0` | `SUM(pax)` 只累加按桌模式的桌数 | 52 人 |
| **晚餐** | 同午餐 | 11 | 52 人 |
| **体检** | 直接存 pax | 正确 | 正确 |

**根因**：纯 SQL 直接查 `booking_items.pax` 字段，但这个字段对早餐/午餐/晚餐都不能正确表示人数：
- 早餐：不在表里（是派生项）
- 午餐/晚餐：按桌模式 pax 存的是桌数，按人模式存的是 0

### 1.6 修复方案（feat/143 第二版 commit `6032fc7`）

后端 `/orders/monthly-pax` 路由从纯 SQL 改为 **SQL + JS 解析**：

| 业务 | 计算方式 |
|---|---|
| 体检 | 直接 `SUM(pax)` |
| 早餐 | 查该月所有 checkup + lodging items → 复用 `deriveBreakfastItems()` 派生 → 每天取 `Math.max(checkupPax, lodgingPax)` 后累加 |
| 午餐 | 解析 `extra.sessions`：按桌模式 = `tables × perTable`，按人模式 = `Σ sessions[].pax` |
| 晚餐 | 同午餐 |

**关键代码**（[booking-board.js](file:///f:/OA/backend/routes/booking-board.js)）：

```js
// ① 体检：直接 SUM(pax)
const [checkupRows] = await pool.query(
  `SELECT COALESCE(SUM(pax), 0) AS total_pax
   FROM booking_items
   WHERE date BETWEEN ? AND ? AND item_type = 'checkup' AND pax > 0`,
  [start, end]
);

// ② 早餐：复用 deriveBreakfastItems 派生
const [bfSourceRows] = await pool.query(
  `SELECT item_type, date, pax, extra
   FROM booking_items
   WHERE date BETWEEN ? AND ? AND item_type IN ('checkup','lodging')`,
  [start, end]
);
const bfSourceItems = bfSourceRows.map(normalizeItem);
const derivedBreakfasts = deriveBreakfastItems(bfSourceItems);
const breakfastTotal = derivedBreakfasts.reduce((s, b) => s + (Number(b.pax) || 0), 0);

// ③ 午餐/晚餐：解析 extra.sessions
for (const row of mealRows) {
  const extra = parseMaybeJson(row.extra) || {};
  const sessions = Array.isArray(extra.sessions) ? extra.sessions : [];
  let mealPax = 0;
  if (sessions.length > 0) {
    for (const s of sessions) {
      const pricingMode = s.pricingMode || 'per_table';
      if (pricingMode === 'per_person') {
        mealPax += Number(s.pax) || 0;
      } else {
        mealPax += (Number(s.tables) || 0) * (Number(s.perTable) || 0);
      }
    }
  } else {
    mealPax = Number(row.pax) || 0;  // 旧数据兜底
  }
  if (row.item_type === 'lunch') lunchTotal += mealPax;
  else if (row.item_type === 'dinner') dinnerTotal += mealPax;
}
```

## 二、医用棉签8cm 单位换算（支→包）数据修正

### 2.1 背景

物资"医用棉签8cm"原单位为"支"，参考单价 0.3 元/支。但实际采购价是 0.025 元/支，系统价格字段为 `DECIMAL(10,2)`（2位小数），无法录入 0.025。用户希望改单位为"包"（1包=2000支），单价 50 元/包（0.025 × 2000 = 50）。

### 2.2 根因：价格精度限制

| 字段 | 类型 | 限制 |
|---|---|---|
| `warehouse_items.reference_price` | `DECIMAL(10,2)` | 最多2位小数，0.025 存不了 |
| `stock_movements.unit_price` | `DECIMAL(10,2)` | 同上 |
| `warehouse_purchase_items.requested_unit_price` | `DECIMAL(10,2)` | 同上 |

前端 `step="0.01"` 也限制只能输入2位小数。

### 2.3 影响分析（改单位对历史数据的影响）

| 表/字段 | 改单位后 | 风险 |
|---|---|---|
| `warehouse_items.unit` | 改为"包" | 主数据，无风险 |
| `warehouse_items.reference_price` | 改为 50.00 | 只影响未来默认单价 |
| `inventory.unit` | **必须同步改**为"包" | ⚠️ 否则主数据"包" vs 库存"支"不一致 |
| `inventory.quantity` | **必须换算**：7400 / 2000 = 3.7 | ⚠️ 不换算则数量含义混乱 |
| `stock_movements.unit` | 不动（快照） | 历史流水保留"支"，正常留痕 |
| `warehouse_purchase_items.requested_unit/received_unit` | 不动（快照） | 历史采购单保留"支" |
| `stock_take_items.unit` | 不动（快照） | 历史盘点单保留"支" |

### 2.4 关键风险：改单位后不能再修改历史采购单收货

`reversePurchaseStock`（[warehouse-purchases.js L2583](file:///f:/OA/backend/routes/warehouse-purchases.js#L2583)）冲回逻辑：
- 旧入库流水 quantity 是"支"（如 7400）
- 改单位后 inventory.quantity 是"包"（3.7）
- 冲回时 `3.7 - 7400 = 负数` → **校验失败，无法修改收货**

**结论**：改单位后，WH20260829001（及所有该物品的历史采购单）永久不能再修改收货。

### 2.5 执行的 SQL

```sql
-- 1. 改主数据单位和单价
UPDATE warehouse_items 
SET unit='包', reference_price=50.00 
WHERE name='医用棉签8cm';

-- 2. 改库存单位 + 换算数量（1包=2000支，7400支→3.7包）
UPDATE inventory i
JOIN warehouse_items wi ON i.item_id = wi.id
SET i.unit='包', i.quantity = 3.7
WHERE wi.name='医用棉签8cm';

-- 验证
SELECT wi.name, wi.unit, wi.reference_price, i.quantity, i.unit AS inv_unit
FROM warehouse_items wi
LEFT JOIN inventory i ON i.item_id = wi.id
WHERE wi.name='医用棉签8cm';
```

### 2.6 执行结果

| name | unit | reference_price | quantity | inv_unit |
|---|---|---|---|---|
| 医用棉签8cm | 包 | 50.00 | 3.7 | 包 |

### 2.7 长期方案（未执行）

把所有价格字段从 `DECIMAL(10,2)` 升级到 `DECIMAL(10,4)`，彻底解决低价物品精度问题。但用户确认未来低价物品入库时会按大单位录入，暂不需要全局升级。

## 三、踩坑 & 教训

### 3.1 派生项不能纯 SQL 聚合

**教训**：早餐不在 `booking_items` 表里，是 `deriveBreakfastItems` 在读取订单时动态生成的派生项。纯 SQL 聚合 `SUM(pax)` 对早餐查到 0。**派生项必须复用派生函数计算，不能直接查表**。

### 3.2 pax 字段语义因业务而异

**教训**：`booking_items.pax` 字段对不同业务含义不同：
- 体检：直接是人数
- 早餐：不在表里（派生）
- 午餐/晚餐按桌模式：存的是桌数（不是人数！）
- 午餐/晚餐按人模式：存的是 0（人数在 `extra.sessions[].pax`）

**聚合人数时必须按业务类型分别处理**，不能一刀切 `SUM(pax)`。

### 3.3 早餐派生规则是 Math.max 不是相加

**教训**：体检和住宿同时存在时，早餐人数取 `Math.max(checkupPax, lodgingPax)`（[L412](file:///f:/OA/backend/routes/booking-board.js#L412)），不是两者相加。这是因为体检客户和住宿客户可能是同一批人，取最大值避免重复计算。

### 3.4 cherry-pick merge commit 麻烦，直接 checkout 文件更简单

**教训**：cherry-pick 一个 amend 产生的 merge commit 需要 `-m 1` 且容易冲突。**更简单的方式**：直接 `git checkout <source-branch> -- <files>` 拿源分支的最终文件状态，然后 commit。跳过 cherry-pick 的合并冲突处理。

### 3.5 amend 前必须确认当前分支（第二次踩坑）

**教训**：feat/140 已踩过一次（amend 误在 main 执行），feat/143 又踩一次。**amend 前必须 `git branch --show-current` 确认在功能分支上**，不能假设。

### 3.6 价格字段 DECIMAL(10,2) 不支持3位小数，低价物品必须用大单位录入

**教训**：所有价格字段（`reference_price` / `unit_price` / `requested_unit_price` / `received_unit_price` / `total_amount`）都是 `DECIMAL(10,2)`，前端 `step="0.01"`。0.025 元/支这类价格无法录入。**解决方案**：改用大单位（支→包，1包=2000支，单价 50 元/包），让单价落在2位小数范围内。长期可升级为 `DECIMAL(10,4)`。

### 3.7 改物品单位必须同步改 inventory.unit + 换算 quantity

**教训**：`warehouse_items.unit` 和 `inventory.unit` 是两个独立字段。只改主数据单位会导致主数据"包" vs 库存"支"不一致，下次入库时 `UPDATE inventory SET quantity = quantity + ?, unit = ?` 会把数量直接相加（100支 + 5包 = 混乱）。**改单位时必须**：① `UPDATE inventory SET unit='新单位', quantity = quantity / 换算比例`。

### 3.8 改单位后历史采购单不能再修改收货

**教训**：`reversePurchaseStock` 冲回逻辑用旧入库流水的 quantity（旧单位）减去当前 inventory.quantity（新单位），会变成负数导致校验失败。**改单位前必须确认**：该物品所有历史采购单都不再需要修改收货。如需修改收货，必须在改单位之前完成。

## 四、约束性内容（已写入项目记忆）

1. **派生项不能纯 SQL 聚合**（feat/143）：早餐是 `deriveBreakfastItems` 派生项不在 booking_items 表，纯 SQL 聚合 SUM(pax) 查到 0。派生项必须复用派生函数。
2. **pax 字段语义因业务而异**（feat/143）：体检直接存人数；午餐/晚餐按桌模式存桌数、按人模式存 0（人数在 extra.sessions）。聚合人数必须按业务类型分别处理。

4. **cherry-pick merge commit 用 checkout 文件代替**（feat/143）：amend 产生的 merge commit cherry-pick 易冲突，直接 `git checkout <branch> -- <files>` 拿最终文件状态更简单。
5. **amend 前必须确认当前分支**（feat/143，第二次踩坑）：feat/140 和 feat/143 都踩过。amend 前 `git branch --show-current` 确认在功能分支。

### 1.2 深挖：从占位名到真实姓名的追溯链

| 段                                                  | 查询                                                                                                            | 输出              |

**最终补偿 SQL**（用 warehouse.manager\_userid → users.wecom\_userid JOIN）：

```sql
UPDATE stock_movements sm
INNER JOIN stock_takes st ON sm.related_id = st.id
INNER JOIN warehouses w ON st.warehouse_id = w.id
LEFT JOIN users u_mgr ON u_mgr.wecom_userid = w.manager_userid
LEFT JOIN users u_cfm ON u_cfm.wecom_userid = w.confirmer_userid
SET sm.operator_id   = COALESCE(u_mgr.id, u_cfm.id, sm.operator_id),
    sm.operator_name = COALESCE(u_mgr.name, u_cfm.name, sm.operator_name)
WHERE sm.movement_type='adjust' AND sm.related_type='take'
  AND sm.id = 'a83c3541-2a38-4c33-8f63-3ab30b0523d7';
```

### 6.2 根因分析：对比另外 3 个 Tab 的 PDF 路由

| Tab        | PDF 生成模式                              | SQL GROUP BY                                          | matrix 构造                        |
| ---------- | ------------------------------------- | ----------------------------------------------------- | -------------------------------- |
| ① 固定资产库存   | `buildMatrix() + generateReportPDF()` | 真实列名（wc.id, wc.parent\_id, w\.department\_id, d.name） | 复用 buildMatrix（内部统一 formatMoney） |
| ② 原材料消耗    | 同上                                    | 从 fetchMaterialConsumptionRows 来                      | 复用 buildMatrix                   |
| ③ 部门费用明细   | 自己 new PDFDocument 逐行画                | 无 matrix                                              | 自己控制                             |
| ④ 供应商统计 ⚠️ | 用了 generateReportPDF，但**手写 matrix**   | **GROUP BY SELECT 别名**（group\_key, supplier\_name）    | 手写 matrix（不走 buildMatrix）        |

**根因**：供应商 PDF SQL 的 `GROUP BY group_key, supplier_name` 引用了 SELECT 别名，其中 `supplier_name = COALESCE(NULLIF(wp.supplier_name, ''), s.name, '无供应商采购')` 依赖 **LEFT JOIN suppliers s** 附表列。MySQL `ONLY_FULL_GROUP_BY` 模式判定 LEFT JOIN 附表列**函数依赖不确定**，报错 `not functionally dependent on columns in GROUP BY clause`。

固定资产/原材料消耗 PDF 不报错的原因：GROUP BY 全部用**真实列名**（不是 SELECT 别名），每一列都直接对应 JOIN 链中确定的关系。

### 6.3 修复方案：完全复用固定资产 PDF 模板

把供应商 PDF 路由改成与固定资产/原材料消耗**完全一致的三段式**：

1. **SQL 改为子查询结构**：内层子查询先算好 `group_key`/`supplier_name`/`amount`，外层 SELECT 把它们映射为 buildMatrix 期望的标准字段（`category_id`/`category`/`category_parent_id`/`category_parent`/`dept_id`/`dept_name`/`amount`），外层 GROUP BY 子查询的真实列 `t.group_key, t.supplier_name`（消除 ONLY\_FULL\_GROUP\_BY）
2. **复用 buildMatrix**：构造假 `deptRows = [{ id: 'amount', name: '采购金额' }]`，`allCategories = []`（由 buildMatrix 从行数据自动构建 L1「供应商统计」→ L2 各供应商）
3. **复用 generateReportPDF**：与另两个 Tab 一字不差

### 6.4 关键 SQL 改动

```sql
-- 改前（报错）：GROUP BY SELECT 别名，supplier_name 含 LEFT JOIN 附表列
GROUP BY group_key, supplier_name

-- 改后（不报错）：子查询先算，外层 GROUP BY 子查询真实列
SELECT t.group_key as category_id, t.supplier_name as category, ...
FROM (
  SELECT CASE ... END as group_key,
         COALESCE(NULLIF(wp.supplier_name, ''), s.name, '无供应商采购') as supplier_name,
         CASE WHEN ... END as amount
  FROM warehouse_purchases wp
  LEFT JOIN suppliers s ON wp.supplier_id = s.id
  INNER JOIN (...) sm ON sm.related_id = wp.id
  WHERE ...
) t
GROUP BY t.group_key, t.supplier_name
```

### 6.6 踩坑教训

1. **GROUP BY 禁止用 SELECT 别名（特别是含 LEFT JOIN 附表列的表达式）**：MySQL `ONLY_FULL_GROUP_BY` 模式下，GROUP BY 引用 SELECT 别名时，如果别名表达式含 LEFT JOIN 附表列（如 `COALESCE(..., s.name, ...)`），会报 `not functionally dependent`。正确做法：用子查询先算好别名，外层 GROUP BY 子查询的真实列；或 GROUP BY 直接写真实表列名。
2. **PDF 路由必须复用 buildMatrix + generateReportPDF**：不要手写 matrix 对象。buildMatrix 内部统一用 `formatMoney()` 包装 values/totals/grandTotal，手写 matrix 容易遗漏这个包装导致格式不一致。新增 PDF 报表路由时，固定模式：(1) SQL 输出 buildMatrix 期望字段（category\_id/category/category\_parent\_id/category\_parent/dept\_id/dept\_name/amount）→ (2) `buildMatrix(rows, deptIdsSorted, deptNameMap, allCategories)` → (3) `generateReportPDF({ title, subtitle, matrix })`。
3. **not\_arrived=1 的物资金额必须剔除**：warehouse-purchases.js L1629-1631 `if (i.not_arrived) return s;` 是业务代码自己的规则——未到货物资不计入总金额。明细接口的行项目金额 SUM 必须加 `CASE WHEN IFNULL(wpi.not_arrived, 0) = 1 THEN 0` 剔除，否则 `received_amount=NULL` 时回退到 `requested_amount`（申购金额），把未到货物资的申购金额误算进统计（feat/108 ¥202.80 差额根因）。

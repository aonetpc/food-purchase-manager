## 二、出错的地方（重点记录）

### 🔴 出错1：`fromBackend` 字段名转换导致 pricing_mode 全程失效

**这是昨日最严重的错误，如果不是在检查代码时发现，按人头计费功能部署后会完全失效（总是 fallback 到 per_room）。**

📌 **完整错误链路**：

```
后端 SQL SELECT * → 返回 { pricing_mode: 'per_person', code: 'RM001', ... }（snake_case）
       ↓
api.ts roomTypes.map(fromBackend) → transformKeys 递归 snake→camel
       ↓
结果变成 { pricingMode: 'per_person', code: 'RM001', ... }（camelCase）
       ↓
Create.tsx 中：(rt as any).pricing_mode → undefined（因为字段名已被改成 pricingMode）
       ↓
所有判断处 `|| 'per_room'` 兜底 → 全部按间计费，按人头功能完全不生效
```

📌 **问题隐蔽性**：
1. 代码中没有任何 TypeScript 报错，因为用到了 `(rt as any)` 断言
2. 页面上也不会报错，只是 silently fallback 到按间计费
3. 只有实际选择"按人头"房型创建订单、手动核对金额时才能发现

📌 **修复**：
```typescript
// 修复前（有问题）：
roomTypes: (d.roomTypes || d.room_types || []).map(fromBackend),

// 修复后（与 wellnessTypes、mealTypes 一致）：
roomTypes: (d.roomTypes || d.room_types || []) as RoomTypeRow[],
```

理由：wellnessTypes、mealTypes 也都是 snake_case 存储，渲染代码统一用 `row.pricing_mode`、`row.unit_price` 等 snake_case 读取。roomTypes 之前独⾃走了 `fromBackend`，造成不一致。

📌 **教训**：
1. **同一类数据结构必须统一字段命名策略**：要么全部 snake_case，要么全部 camelCase，不能混用
2. **`(as any)` 断言会屏蔽掉字段名错误**：使用前必须确认字段存在性（可以加 `console.log` 在开发期打印）
3. **配置类接口涉及 ENUM 切换字段时，必须单独端到端验证**：不能只验证"能保存"，还要验证"从保存→读取→UI展示→计算→保存"完整闭环
4. **本次检查方法**：git diff 后发现代码大量使用 `(rt as any).pricing_mode`，但 api.ts 中 roomTypes 走了 `fromBackend`，两者不一致 → 反向推导出问题

### 🟡 出错3：fallback 硬编码房型缺少 pricing_mode 字段

📌 **错误过程**：
1. `finalRoomOptions` 的 fallback 数组（`roomOptions` 为空时使用的兜底数据）写的是：
   ```
   { id: 'fb_std', code: 'standard', name: '标准间', price: 480, status: 1, sort_order: 1 }
   ```
   没有 `pricing_mode` 字段
2. 当业务配置为空（新系统首次启动/迁移未执行等情况），所有代码中 `rt.pricing_mode || 'per_room'` 虽然能兜底，但这属于"隐性依赖默认值"，不是最佳实践

📌 **修复**：fallback 数据中显式补上 `pricing_mode: 'per_room'`，与真实数据结构完全一致。

📌 **教训**：
- **fallback 数据结构必须与真实数据 100% 一致**，包括可选字段（哪怕有默认值也写上）
- 这样可以避免某些"严格判断字段存在性"的代码在 fallback 场景下走不同分支

## 三、需要注意的地方

### ⚠️ 注意1：`fromBackend` 对不同类型配置使用策略不一致

当前 `getConfig()` 中各配置的字段转换策略：

| 配置类型 | 转换方式 | 字段命名 |
|---------|---------|---------|
| `packages` | 特殊处理 + items 还原 snake_case | 混合 |
| `roomTypes` | ✅ 不转换（08-21 修复后） | snake_case |
| `meetingHalls` | ❌ 还在走 `fromBackend` | camelCase（与其他不一致！） |
| `wellnessTypes` | ✅ 不转换 | snake_case |
| `mealTypes` | ✅ 不转换 | snake_case |
| `checkupItems` | ✅ 不转换 | snake_case |
| `salesUsers` | ❌ 还在走 `fromBackend` | camelCase |

`meetingHalls` 和 `salesUsers` 目前仍走 `fromBackend`，如果后续要对这两类配置新增 snake_case 字段（如 `half_price` 读取），可能踩到同样的陷阱。建议后续统一改为不转换。

---

### ⚠️ 注意2：住宿功能涉及的字段命名策略

| 场景 | 计价方式字段名 | 数据类型 | 位置 |
|------|-------------|---------|------|
| 房型配置表 row | `pricing_mode` | snake_case | `RoomTypeRow` / 后端返回 |
| 会话状态（内存） | `pricingMode` | camelCase | `LodgingSession`（Create.tsx） |
| 订单 extra（持久化） | `pricingMode` | camelCase | `ItemExtra` / JSON 存储 |

**故意设计为"配置层 snake_case、业务层 camelCase"**：
- 配置层贴近数据库，保持 snake_case
- 业务状态和 extra 贴近前端 React state，保持 camelCase（与 `lodgingType`、`dateCheckIn` 等一致）
- 两处转换发生在：① 点击房型胶囊时从 `pricing_mode` → `pricingMode`；② 保存/计算时从会话 `pricingMode` 传入 calc 函数

后续维护时注意不要混淆。

## 四、关键决策记录

### 决策 1：选择方案 A（房型级 pricing_mode 字段）而不是其他方案

- **备选方案回顾**：
  | 方案 | 思路 | 优点 | 缺点 |
  |------|------|------|------|
  | **A（选中）** | 房型级新增 `pricing_mode`，全局双模式 | 改动集中，订单维度清晰，管理员配置即可 | 需改 8 个文件 |
  | B | 订单维度单独字段指定 | 灵活性高 | 每个订单每次都要手动选，操作量大 |
  | C | 仅前端计算时按输入单位判断 | 不改数据库 | 持久化无记录，报表/导出时无法还原 |

- **决策理由**：
  1. 计价方式是房型的**固有属性**（如"学生宿舍"天生按人、"大床房"天生按间），应该在房型级配置而不是订单级
  2. 持久化写入 extra 保证订单数据**自洽**（后续导出/报表/打印不需要再反查配置）
  3. 与用餐标准（`mealTypes.pricing_mode` = 按桌/按人）一致的设计模式，代码复用率高

### 决策 2：roomTypes 不走 fromBackend，与 wellness/meal 保持一致

- **选择**：修复 api.ts 中 roomTypes 走 `fromBackend` 的写法，改为与 wellnessTypes、mealTypes 一样直接类型断言
- **原因**：
  1. `fromBackend` 的 snake→camel 转换会导致 `pricing_mode` 等 ENUM 字段名与其他配置类不一致
  2. wellnessTypes/mealTypes 已大量使用 `row.pricing_mode`、`row.unit_price` 等 snake_case 读取，统一策略减少混淆
  3. 修复范围最小（只改 1 行，不用调整大量渲染代码）

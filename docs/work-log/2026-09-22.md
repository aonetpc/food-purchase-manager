## 一、fix/179：附件上传改为二进制先上传再提交，根除 413

### 1.1 背景

用户反映月结付款发起时报 413 Request Entity Too Large。排查发现：
- 前端用 `FileReader.readAsDataURL` 把 PDF 转 base64 塞在 JSON 请求体里
- base64 编码膨胀 33%，937KB 的 PDF 编码后约 1.22MB
- Nginx 默认 `client_max_body_size` 是 1MB，1.22MB > 1MB 触发 413
- Express 本身配了 50MB 够用，但 Nginx 在前面先拦截了

用户确认：不带附件能发起成功，带附件就 413，100% 是附件 base64 编码导致请求体超限。

### 1.2 方案对比

曾考虑两个方案：
- **方案 A（架构修复）**：前端先单独上传附件，再提交付款。全部在仓库里改，走正常部署流程，根治 413
- **方案 B（Nginx 临时扩容）**：SSH 改 Nginx `client_max_body_size 50m`。最快但治标不治本，Nginx 配置不在仓库里

用户选择方案 A，理由：符合自动化部署偏好，根治问题，可一并修仓库采购预付采购的潜在 413。

## 二、fix/180：附件上传显示真实进度条

### 2.1 背景

fix/179 部署后，用户反映附件上传时没有进度条，只是"稍微过了一会时间就显示出附件来了"，慢的时候会让操作者以为没上传。

### 2.2 根因

`api.upload` 用 `fetch` API 实现，**fetch 原生不支持上传进度**——只有 `XMLHttpRequest` 的 `xhr.upload.onprogress` 才能拿到真实进度（基于 `e.loaded/e.total`）。

### 2.3 改动（3 files，+62/-29）

**api.ts** [L97-130](file:///f:/OA/src/lib/api.ts#L97-L130)
- `api.upload` 从 `fetch` 改为 `XMLHttpRequest`
- 新增 `options?: { onProgress?: (percent: number) => void }` 回调参数
- `xhr.upload.onprogress` 基于 `e.loaded/e.total` 计算真实百分比
- 保留 `X-Filename` 头 + `Authorization` 头 + 超时处理

**前端 SupplierReconciliation/index.tsx** [L125](file:///f:/OA/src/pages/SupplierReconciliation/index.tsx#L125)
- 新增 `paymentUploadProgress` state（`number | null`）
- `handleFileUpload` 循环内每个文件上传前 `setPaymentUploadProgress(0)`，上传中 `onProgress` 更新百分比，完成后 `setPaymentUploadProgress(null)`
- 附件区域 UI：`paymentUploadProgress !== null` 时显示蓝色（indigo）进度条 + "上传中 XX%"

**前端 WarehousePurchase/index.tsx** [L244](file:///f:/OA/src/pages/WarehousePurchase/index.tsx#L244)
- 新增 `prepayUploadProgress` state
- `handlePrepayFileChange` 同样改造
- 附件区域 UI：显示橙色（orange）进度条 + "上传中 XX%"

### 2.4 验证

- 前端 `npm run build` 构建成功（13.94s）
- commit `572a045`
- 基于 fix/179 分支创建，包含 fix/179 全部改动

### 2.5 关键决策

- **真实进度而非假动画**：用 XHR `upload.onprogress` 的 `e.loaded/e.total` 计算百分比，是真实的网络传输进度，不是定时器假动画

## 三、踩坑教训

1. **fetch 不支持上传进度**：`fetch` API 只能拿到下载进度（`response.body.getReader()`），上传进度必须用 `XMLHttpRequest` 的 `xhr.upload.onprogress`。需要进度反馈的上传场景不要用 fetch
2. **base64 编码膨胀 33%**：PDF/图片转 base64 后体积膨胀约 33%，937KB → 1.22MB，容易触发 Nginx 默认 1MB 的 `client_max_body_size` 限制。附件上传应直接发送二进制，不要转 base64
3. **Nginx 在 Express 前面会先拦截**：即使 Express 配了 `express.json({ limit: '50mb' })`，Nginx 的 `client_max_body_size` 默认 1MB 会先拦截大请求体。排查 413 时优先检查 Nginx 配置
4. **跨页面复用模式时注意变量名**：仓库采购的函数名是 `handlePrepayFileChange`（不是 `handleFileUpload`），JSX 调用点 `onChange={handlePrepayFileChange}` 必须与函数名一致，改名要同步改 JSX

## 一、完成事项

### 1.1 feat/215：采购单展开区显示实际入库金额与入库时间

**背景**：用户截图反馈仓库采购订单卡片信息冗余——折叠头部信息条已显示「采购单号 · 仓库 · 总金额 ¥2,936.00 · 创建时间 · 创建人」，展开后「基本信息」四宫格（采购单号 / 入库仓库 / 总金额 / 创建时间）把同样的信息又显示一遍，而审批真正关心的「实际入库金额」「入库时间」两个关键信息反而缺失。

**现状盘点（代码核对）**：

| 展开区四宫格 | 折叠头部 | 结论 |
|---|---|---|
| 采购单号 | 标题行已有 | 重复 |
| 入库仓库 | 已有（多仓时显示「后勤仓库 (2个)」） | 重复但展开格有完整仓库列表，保留 |
| 总金额 | 已有（同一数值） | 重复 |
| 创建时间 | 已有 | 重复 |

**数据可行性核对**：

- 实际入库金额：`warehouse_purchases.actual_amount` 早已存在（迁移 034，字段注释「实际收货总金额」），收货接口按 `Σ received_quantity × received_unit_price` 写入，`normalizePurchaseRow` 已返回；前端仅缺类型声明
- 入库时间：**无此字段**。`created_at` 是下单时间，`confirmed_at` 是「确认」阶段完成时间（迁移 055），而库存是在流程上一步「收货」时写入 `inventory` 的——两个时间戳语义不同，不能混用

**方案演进（关键转折）**：

1. 初版方案：新增 `warehouse_purchases.received_at` 列 + 迁移脚本 + 首次收货写入（需存量回填）
2. 用户补充证据：出入库记录页最左侧「时间」列已展示入库时间——核对代码确认该列取 `stock_movements.created_at`，收货时与库存同步写入（`movement_type='inbound'`, `related_type='purchase'`, `related_id=采购单id`）
3. 最终方案：入库时间改为从流水**派生**，在详情接口 `GET /:id` 加一条查询：

```sql
SELECT MIN(created_at) AS received_at FROM stock_movements
WHERE related_type = 'purchase' AND related_id = ? AND movement_type = 'inbound'
```

派生方案胜出的三个理由：① 零迁移零回填，历史已收货订单天然有值；② 与出入库记录页同一数据源，两页永远一致；③ 「修改收货」会经 `reversePurchaseStock` 删旧流水再重插，同时 `actual_amount` 被覆盖为最新值——派生时间同步反映「当前生效的这次收货」，金额与时间口径一致。

**改动（2 文件，+15/-4，零迁移）**：

1. [warehouse-purchases.js](../../backend/routes/warehouse-purchases.js) `GET /:id` 详情接口：追加 `MIN(created_at)` 派生查询，返回 `received_at`（未收货为 `null`）。SQL 必须带 `movement_type='inbound'` 过滤——即买即用物资收货时同时产生 inbound + expense 两条流水，不过滤会取错
2. [WarehousePurchase/index.tsx](../../src/pages/WarehousePurchase/index.tsx)：
   - interface 补 `actual_amount?: number`、`received_at?: string | null`
   - 四宫格第 3/4 格：总金额 → **实际入库金额**（`received_at` 为空显示 `-`，不显示 ¥0.00 防止误读为「收货了但金额为 0」；取值兜底 `actual_amount ?? total_amount`）、创建时间 → **入库时间**（空显示 `-`）
   - 采购单号、入库仓库两格保留（单据标识 + 多仓完整列表仍有价值）

**数据链路确认**：展开卡片时前端调详情接口并 `{ ...it, ...detail }` 合并进列表数据，`received_at` / `actual_amount` 随详情到位；仅详情接口需要该字段，列表接口不加查询。

**验证**：`node --check` 后端语法通过；`npm run build` 通过（13.34s）。

## 三、关键决策记录

### 3.1 替换而非新增

展开区四宫格与折叠头部 100% 重复。不新增卡片/行，直接把「总金额」「创建时间」两个槽位替换为「实际入库金额」「入库时间」——金额对金额、时间对时间，栅格与视觉层级零调整，折叠头部仍保留申请总金额，上下形成「申请 vs 实收」对比。

### 3.2 入库时间从流水派生，不新增数据库列

用户提供的「出入库记录页已有入库时间」证据直接推翻初版加列方案：加列要迁移 + 存量回填，且与流水页形成两个数据源，「修改收货」后必然漂移；派生方案零迁移、天然同源、历史单有值。若未来列表折叠行或导出场景也要用入库时间，再考虑落列。

### 3.3 入库时间语义 = 最近一次收货时间（非首次）

修改收货会删除旧流水并重插，`actual_amount` 也同步覆盖为最新值。三者（流水页时间、采购卡片入库时间、实际入库金额）统一反映「当前生效的这次收货」，不做首次时间守卫。已向用户明示并确认。

### 3.4 未收货显示 `-`

草稿/审批中订单没有实际入库金额和入库时间，显示 `-`；金额不显示 ¥0.00，避免被误读为「已收货但金额为零」。

## 五、踩坑教训

1. **业务时间字段先查「是否已有事件/流水表可派生」，别急着加列**（ref：feat/215，2026-10-15）：初版直接设计 `received_at` 新列 + 迁移 + 回填，用户一句「出入库记录里已经有入库时间」点醒——`stock_movements.created_at` 早就在记录。固定动作：需要「某动作发生时间」时，先 grep 该动作是否已写流水/日志表（stock_movements、flow_logs 等），能派生就不加列；加列的代价是迁移、存量回填、双数据源一致性维护。

2. **同一流程中相邻步骤的时间戳不能混用**（ref：feat/215，2026-10-15）：采购流程是「草稿→审批→**收货**→**确认**→报销→完成」，`confirmed_at`（迁移 055，确认完成时间）不是入库时间，库存是在收货时进入 inventory 的。截图证据：单据 10-09 创建、10-15 才入库，相差 6 天。复用相邻步骤时间戳前必须先核对该字段是在哪一步、哪条 SQL 写入的。

3. **派生时间的 SQL 必须过滤同一业务动作产生的多种流水类型**（ref：feat/215，2026-10-15）：采购收货对即买即用物资会同时写 inbound（入库）和 expense（自动出库）两条 stock_movements，若只按 `related_type + related_id` 取 MIN，会把自动出库时间也算进去。固定动作：写流水派生查询前先 grep 该业务往流水表写了哪几种 movement_type。

4. **折叠/展开两层 UI 的信息不应重复，展开层展示「深一层」信息**（ref：feat/215，2026-10-15）：折叠行承担列表扫读（单号/仓库/申请总额/创建时间/状态），展开层应展示只有详情才需要的信息（实收金额、入库时间、明细、确认进度）。信息去重时优先做「同语义槽位替换」（金额换金额、时间换时间），布局改动最小。

5. **用户补充的现场截图是方案降级的关键证据，要立即据证修正方案而非辩护原方案**（ref：feat/215，2026-10-15）：初版方案（加列+迁移）在技术上完全可行，但用户补充的流水页截图证明数据已存在——方案从「1 条迁移 + 3 处改动」降到「3 处纯代码改动，零迁移」。与 feat/205「复制按钮」教训同源：用户的事实证据优先于自己的初始设计。

6. **金额空值兜底要防 ¥0.00 误读**（ref：feat/215，2026-10-15）：未收货时 actual_amount 为 0，直接 formatCurrency 会显示 ¥0.00，用户无法区分「未收货」和「收货了但金额为 0」。以 received_at 是否存在作为「是否发生过入库」的总开关，未入库金额/时间统一显示 `-`。

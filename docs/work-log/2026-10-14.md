### 1.1 feat/210：H5 住宿议价徽章显示折扣率

**背景**：用户截图反馈 H5 预订确认单的住宿卡片显示「议价」徽章，说明房价有折扣，但看不到折扣率，也无法对比议价便宜了多少。

**分析**：
- H5 `LodgingDetails` 组件已有 `displayStd`（同口径标准价，来自房型配置）和 `customPrice`（议价），折扣率可前端直接计算，无需改后端/DB
- 住宿 DB 只存 `extra.customPrice`，不存 `discount_rate`、不存 `basePrice`
- 当时的问题：议价时同口径标准价被隐藏，只显示另一口径的参考价

**方案确认**：向用户提供 A（徽章+原价删除线）/ B（仅徽章加折扣率）/ C（电商风并列）三个方案，用户选择**方案 B**：只把徽章从「议价」改为「议价 X.X折」，折扣格式用 `7.8折` 与体检展示一致。

**改动**：[src/pages/BookingConfirm/index.tsx](../../src/pages/BookingConfirm/index.tsx) `LodgingDetails` 组件（+11/-1）：

```ts
const hasDiscount = hasCustom && displayStd > 0 && customPrice < displayStd;
const discountLabel = hasDiscount
  ? `${(Math.round((customPrice / displayStd) * 100) / 10).toFixed(1)}折`
  : '';
// 徽章：议价{hasDiscount ? ` ${discountLabel}` : ''}
```

**边界处理**：标准价≤0、议价≥标准价、无议价 → 只显示「议价」或无徽章。

### 1.2 feat/211：议价标识逻辑修正 + 标准价快照

**背景**：feat/210 部署后，用户截图反馈已发起的订单仍只显示「议价」，没有折扣率。分析发现截图中三单的议价恰好等于当前房型配置标准价（竹風別墅双床/大床 ¥2,880=¥2,880，稻香山林双床 ¥1,118=¥1,118），`customPrice < displayStd` 不成立所以不显示折扣率——**但用户追问：「如果等于标准价的话，不应该显示议价这个标识啊？」**，确认这是逻辑缺陷：H5 端徽章条件是 `hasCustom`（填了议价就显示），缺少 PC 端已有的「议价≠标准价」判断。

**问题根因（两层）**：
1. **徽章条件缺失**：H5 用 `hasCustom` 判断，PC 端 [Create.tsx](../../src/pages/BookingBoard/Create.tsx) 已有 `isNegotiated = hasCustom && Number(s.customPrice) !== basePrice`，两端不同步
2. **对比基准失真**：住宿 `extra` 只存 `customPrice`，不存下单时标准价；折扣率用「渲染时当前配置价」计算，下单后标准价被改则历史订单折扣率失真

**改动（3 文件，+30/-25）**：

1. [utils.ts](../../src/pages/BookingBoard/utils.ts)：新增 `getLodgingBasePrice(lodgingType, config, pricingMode)` 辅助函数（取房型在指定口径下的标准单价），`calcLodgingAmount` 复用它消除重复逻辑
2. [Create.tsx](../../src/pages/BookingBoard/Create.tsx)：保存住宿项时 `extra` 写入 `basePriceSnapshot`（下单时同口径标准价快照），参照已有的 `bedsPerRoomSnapshot` 模式
3. [BookingConfirm/index.tsx](../../src/pages/BookingConfirm/index.tsx)：

```ts
// 对比基准：优先用下单时快照，回退当前配置价
const basePrice = Number(extra.basePriceSnapshot) > 0 ? Number(extra.basePriceSnapshot) : displayStd;
// 仅当议价真正不等于标准价时才算议价
const isNegotiated = hasCustom && customPrice !== basePrice;
const hasDiscount = hasCustom && basePrice > 0 && customPrice < basePrice;
// 徽章：{isNegotiated && (...)}
```

**修复后行为**：

| 条件 | 徽章显示 |
|------|---------|
| 无议价 | 不显示 |
| 议价 = 标准价 | **不显示**（本次修复核心） |
| 议价 < 标准价 | `议价 7.8折` |
| 议价 > 标准价 | `议价` |

**对历史订单**：无快照的旧订单回退当前配置价判断；用户截图里议价=标准价的几单，「议价」徽章消失，符合「没议价就不标」预期。

### 1.3 feat/212：预订审批支持串行/并行双模式（配置开关默认串行）

**背景**：用户反馈突发订单较多，「发起订单 → 销售员确认 → 审核员审核」的串行流程严重影响各相关部门的接待，希望压缩审批时延。给出两个备选方向：A 交换审核与确认顺序；B 二者并行处理。

**方案对比结论**：

- 方案 A（发起 → 审核 → 销售确认）只是把瓶颈从审核员换到销售员，总时延不减少，且要处理在途订单——若复用旧状态名，老订单会被误判（可能跳过审核）
- 方案 B（销售确认 ∥ 审核员审核 并行）才能真正压缩时延，且可用「新状态只给新单」天然兼容在途订单

**方案确认**：用户选定方案 B，并明确三点：① 驳回时另一方已签作废、全单重走；② 不放宽审核权，仍保留企微配置的固定审核员；③ 配置开关默认关闭。

**改动（8 文件）**：

1. [119_booking_flow_mode.sql](../../backend/migrations/119_booking_flow_mode.sql)（新增）：`wecom_config.booking_flow_mode` VARCHAR(20) NOT NULL DEFAULT 'serial'，幂等 DDL
2. [wecom.js](../../backend/routes/wecom.js)：配置读写支持开关（非法值回落 serial）；抽出 `sendSalesPendingCard` / `sendApproverPendingCard` 两个 helper（含 42014 task_id 递增重试）供串行/并行复用；提交时并行补发审核卡 + 群消息

4. [booking-reminder.js](../../backend/utils/booking-reminder.js)：新增并导出 `completeStageReminders(orderId, stage)`（按阶段隔离，避免并行下灰化一侧误杀另一侧催办）；`executeOneReminder` 增加「阶段已满足即结束」
5. 前端 [types.ts](../../src/pages/BookingBoard/types.ts) / [constants.ts](../../src/pages/BookingBoard/constants.ts) / [BookingBoard/index.tsx](../../src/pages/BookingBoard/index.tsx) / [BookingConfirm/index.tsx](../../src/pages/BookingConfirm/index.tsx) / [WecomManager/index.tsx](../../src/pages/WecomManager/index.tsx)：新增 `parallel_sign` 状态展示与「审批流程模式」单选

**核心语义**：

### 1.5 feat/214：驳回单修改后自动重新发起审批

**背景**：用户反馈驳回单在预订调度只有「修改此单」按钮，修改保存后不会重新发起确认/审核消息。

**方案确认**：方案 A + 区分文案——修改驳回单 = 自动重新发起，并加保存前二次确认防误操作。

**改动（4 文件，+75/-1）**：

## 三、关键决策记录

### 3.1 方案 B（仅徽章加折扣率）而非 A/C

用户选择最省改动的方案：不改主单价区布局、不加原价删除线，只在「议价」徽章右侧拼接折扣率。信息够用且 H5 窄屏不拥挤。

### 3.2 折扣格式统一为「X.X折」

`formatDiscountInfo` 的计算分支返回「78折」、体检 DB 分支返回「7.8折」，中文惯例更通用「7.8折」。住宿折扣率用 `(Math.round((customPrice / basePrice) * 100) / 10).toFixed(1)折` 与体检展示一致。

### 3.3 快照模式复用 bedsPerRoomSnapshot 先例

下单时把同口径标准价存入 `extra.basePriceSnapshot`，与早餐床位快照同一模式：配置变更不影响历史订单的展示。H5 渲染时 `basePrice = 快照 ?? 当前配置价`，新订单历史准确，旧订单回退兼容，无需迁移脚本。

### 3.4 不动后端、不动 DB、不动金额计算

两轮改动均在展示层：feat/210 只动 H5 徽章；feat/211 的快照字段写在 `extra` JSON 内（无表结构变更），`calcLodgingAmount` 重构为复用 `getLodgingBasePrice` 但计算逻辑零变化。

### 3.5 审批用方案 B（并行）而非方案 A（交换顺序）

方案 A 把瓶颈从审核员换成销售员，总时延不减少，且必须处理在途订单；方案 B 让两方同时处理，真正压缩时延。用户确认选 B。

### 3.6 新状态 `parallel_sign` + 配置开关默认 `serial`

不硬改流程，而是「新状态只给新单 + 开关默认关闭」：老订单继续走老状态老逻辑，新订单走新状态，上线即在但完全不变，可回退可灰度。

### 3.7 驳回 = 全单重走，不放宽审核权

任一方驳回即清空双方签字痕迹、两张卡作废、退回 `rejected`，避免「一方已签、另一方改后仍沿用旧签字」的隐患。审核权保持仅企微配置的固定审核员，admin/booker 不放宽。

### 3.8 群消息状态行由订单数据动态推导，不按模式硬编码

`statusLine` 从 `sales_confirmed_at` / `confirmed_at` 四态推导，串行/并行共用一套文案；删除 `parallelSubmit` 专用分支，差异收敛为可选参数（`sendApproverCard` / `isResubmit`），后续再加流程模式不必再开新文案。

### 3.9 第二方签齐只发一条

避免「X 已签字 + 订单已确认」两条连发刷屏；第一方签字发一条、第二方签齐发一条，消息总数与串行持平但并行下不再断档。

### 3.10 驳回单修改 = 自动重新发起 + 保存前二次确认

驳回单的唯一出路是重走，故编辑保存即自动推进流程并发通知；同时加二次确认弹窗防手滑，并保留「再次编辑 / 撤回 / 驳回后再改」三条恢复路径。

## 五、踩坑教训

1. **「填了议价字段」≠「有议价」，标识条件必须判断议价≠标准价**（ref：feat/211，2026-10-14）：H5 端徽章条件是 `hasCustom`（customPrice 存在即显示），导致议价恰好等于标准价的订单也挂「议价」徽章，用户一眼看出矛盾。PC 端早有 `isNegotiated = hasCustom && customPrice !== basePrice` 判断，H5 端没同步。规则：任何「有优惠/有议价」类标识，显示条件必须包含「优惠值 ≠ 基准值」的实质判断，不能只判断字段存在。

2. **折扣/议价对比的基准价必须用下单时快照，不能用渲染时配置价**（ref：feat/211，2026-10-14）：住宿 extra 只存 customPrice 不存标准价，用当前房型配置价当基准，下单后改配置会让历史订单折扣率失真（甚至把「有折扣」变成「无折扣」）。凡「与基准值对比」的展示，基准值必须在业务发生时快照（本项目先例：`bedsPerRoomSnapshot` → `basePriceSnapshot`），渲染时 `快照 ?? 当前值` 回退兼容旧数据。

3. **用户反馈「没看到效果」先验证边界条件是否成立，不要直接怀疑部署**（ref：feat/210→211，2026-10-14）：部署后用户截图「没有折扣率」，实际是议价=标准价时 `customPrice < displayStd` 不成立，属于边界条件而非部署失败。先拿截图里的实际数值（¥2,880 vs 标准价 ¥2,880）代回显示条件验证，再决定是否改代码。

4. **同一业务 PC/H5 两端判断逻辑必须同步核对**（ref：feat/211，2026-10-14）：PC 端 Create.tsx 已有议价≠标准价的判断，H5 端 LodgingDetails 缺失。新增展示逻辑时 grep PC 端同业务代码（如 `isNegotiated`）核对条件是否一致，避免一端严一端宽。

5. **重构顺手消除重复时要保证行为零变化**（ref：feat/211，2026-10-14）：新增 `getLodgingBasePrice` 时把 `calcLodgingAmount` 内联的 basePrice 计算提取复用，逻辑逐行等价搬运（per_person 分支的 fallback 链 `price_per_person > 0 ? : (pricing_mode==='per_person' ? price : 0)` 原样保留），改完构建验证。

6. **新增订单状态要先盘点「状态机分散耦合点」**（ref：feat/212，2026-10-14）：`parallel_sign` 需同时改后端 7 个 handler 的状态白名单、`EDITABLE_STATUS`、删除白名单、催办 stage 映射，以及前端 types / constants / PC 看板 / H5 确认页 / 企微配置页。漏改任一处会出现状态无法流转或看板不显示。固定动作：先 grep 状态名与各白名单变量，列出命中清单再动手。

7. **「整个订单」维度的批量清理在并行流程下会误杀另一侧**（ref：feat/212，2026-10-14）：`greyAllCardsOnApprove` 按 `order_id` 全清催办，并行下销售签完会把审核侧的催办一起杀掉；改为按阶段隔离的 `completeStageReminders(orderId, stage)`。设计批量操作前先问一句「这个操作的作用域是整单还是单个参与方」。

8. **「新状态只给新单」是让新流程对在途订单零影响的天然手段**（ref：feat/212，2026-10-14）：并行流程用新状态 `parallel_sign`，老订单继续留在老状态走老逻辑，无需任何数据迁移或兼容代码即可上线；若复用旧状态名（如方案 A 交换顺序），在途订单会被误判而跳过校验。

9. **「有功能但入口不可见」与「功能未实现」必须区分**（ref：feat/214，2026-10-14）：用户反馈「驳回单只能改、不会重新发起」，实际后端设计了第二步「提交确认」按钮，藏在详情抽屉里（rejected 时显示），而用户操作路径（卡片 → 修改 → 保存）不经过它。排查固定动作：grep 后端接口是否存在 → grep 前端按钮渲染条件 → 确认入口位置，再判断是补功能还是挪入口。

10. **「编辑保存后不产生后续动作」是流程割裂的典型信号**（ref：feat/214，2026-10-14）：PUT 编辑接口只对 4 种状态做流转，`rejected` 什么都不做，通知函数分支也不覆盖它，用户感知就是「改了没反应」。凡「编辑后应有后续动作」的流程，编辑接口与通知函数必须同时覆盖该状态。

11. **本地合并 main 成功 ≠ 已上线**（ref：feat/214，2026-10-14）：push 因 github.com:443 连接超时失败时，本地 merge 已完成但远端未更新，必须明确告知「未上线、待网络恢复补推」，不得因 `git log` 能看到 merge 提交就宣称完成部署。

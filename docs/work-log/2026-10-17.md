## 三、关键决策记录

### 3.1 申报值随单存档，不再做系统派生

系统比对值因月度盘点滞后、未建档物资覆盖不全而不可靠，继续展示反而误导审批。改为采购人手工申报、落库 `stock_at_purchase` 随单存档——PDF、详情、编辑回填全链路只读落库值，与填报时点一致，不受后续库存变动影响。

### 3.2 粘贴列追加在最后，不插在中间

老的 6/7 列 Excel 模板已是使用习惯，库存列插在中间会导致整行错位；追加末尾后老模板粘贴行为完全不变，新列按需使用。

### 3.3 不预填系统值

预填会让审批人误以为数字来自系统盘点，与「申报」语义矛盾；输入框空白 + placeholder「库存」，纯手填。

### 3.4 非必填 + 0 是合法值

不填存 NULL 显示 `-`；但 0（已断货）是有效申报值，解析时必须用 `isNaN` 判断而非 `|| null` 兜底（`0 || null` 会把 0 吞成 NULL）。

## 五、踩坑教训

1. **系统派生值不可靠时，改为「填报人申报 + 随单存档」比修补派生逻辑更有效**（ref：feat/216，2026-10-17）：库存比对的两个缺口（盘点滞后、未建档物资无 item_id）都无法靠算法补——月中任何时刻系统值都可能失真。让最了解现场的人填数并落库，审批人看的是「采购人申报数」，权责也更清晰。判断信号：派生数据源本身有校准周期（月度盘点）或覆盖盲区（未建档）时，派生展示不如申报存档。

2. **Excel/粘贴类输入格式新增列，一律追加在最后**（ref：feat/216，2026-10-17）：用户已有模板习惯（6/7 列），插中间会整行错位且难以排查；追加末尾对老模板零影响，新列按需启用。解析端按列序号取值，分支格式（有无供应商列）分别标注列序号。

3. **数值字段校验禁用 `||` 兜底，0 会被吞**（ref：feat/216，2026-10-17）：`parseFloat(stock) || null` 会把合法的 0（已断货）吞成 null。固定写法：`const n = parseFloat(s); s.trim() === '' || isNaN(n) ? null : n`。与盘点 H5「尾部零被吞」、扫码领料 draft 模式同属数值输入陷阱族。

4. **下线派生链路要整体清理，不留半截死代码**（ref：feat/216，2026-10-17）：库存列改手工输入后，`/inventory` 拉取、inventoryMap state、getStockInfo 三层同时删除——只删渲染处会留下未使用的 state 和接口调用，TS noUnusedLocals 直接 build 失败；三层同删后构建一次通过。

5. **同一粘贴解析器存在多分支列格式时，加列必须逐分支核对列序号**（ref：feat/216，2026-10-17）：现购 8 列（含供应商）vs 预付/月结 7 列（useFixedSupplier 无供应商列），库存分别是 `cols[7]` 和 `cols[6]`，只改一个分支会导致另一类型把「理由」解析成库存。

6. **提交时间表述以 git 记录为准**（ref：2026-10-16 复盘小错，2026-10-17 修正）：上一轮日志把 feat/215 提交时间误写为「11:51」，git log 实际为 2026-10-15 11:51 提交、11:54 合并——写日志前先 `git log --since/--until` 拉当日提交清单，不凭对话记忆写时间。

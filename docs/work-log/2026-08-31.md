## 三、PDF 数据流分析（重要发现，记入项目记忆）

### 3.1 PDF 不是直接吃前端数据

PDF 后端走完整链路：
```
前端下载按钮 → GET /share/:token/pdf
  → 查 booking_packages WHERE share_token = ?
  → readPackageFull(pkg.id)
    → listPackageItems(packageId)  // SQL: SELECT pi.*, ci.category, ci.item_type
    → aggregateRoleItems(allItems, pkg.applicable_roles) // 按角色 + 可见性合并
    → pkg.role_items = { male: {items:[], total, item_count}, female_married: {...}, ... }
  → 遍历 roles → 遍历 items 调 renderPdfItemsSection
```

**关键**：`listPackageItems` 返回的 item 字段名是 **`item_name_snapshot`**（不是 `name`），有 `category`（科别）但**没有** `sub_category` 字段。所以 `displaySub()` 函数的第 1 行 `if (it.sub_category) return it.sub_category` 永远不走，走的是 `SUB_DISPLAY_NAME[it.category]` 或关键词推断兜底。

**这意味着**：前端 SharePage 和后端 PDF 的分类逻辑**共享 SUB_DISPLAY_NAME 映射表 + 关键词正则推断**，但前后端字段名不同（前端有 `sub_category` 真实值，后端没有）。修 PDF 时要特别注意 displaySub 里对 category 的处理。

### 3.2 PDF 不显示价格是故意的（feat/106 需求）

用户明确要求 PDF 里不显示单项价格。后端实现方式：
1. `renderPdfItemsSection` 是纯名单渲染函数，**不接收价格参数**，只渲染 `item_name_snapshot` + `sub_item_names`
2. 分享 PDF 路由 L1672 直接调 `renderPdfItemsSection(doc, items, { FONT_REG, FONT_BOLD })`，**不传给它价格信息**
3. 套餐顶部的「原价 ¥XXX · 折后价 ¥XXX · 折扣率 XX%」保留（L1667-L1668），底部「合计 ¥XXX」保留（L1674-L1675），只有单项明细里没有价格

**这个设计是对的**：让客户知道"这套大概多少钱"但看不到每个单项的价格，避免销售价被竞品扒。

## 四、今日踩坑 & 教训（续历史 #28~#30，新增 #31~#38）

| # | 踩坑 | 教训 |
|---|------|------|
| 31 | **Header 固定 h-44 + overflow-hidden 叠加 -mt-16 上浮 → 裁掉底部内容**：首轮 Q1 缩头时只考虑了"视觉更紧凑"，没算清楚 4 行内容（品牌+标题+胶囊+有效期）在 176px 容器里放不下 | **改高度类元素先算像素**：10pt body（48px）+ 32pt（h-8）+ 28pt（pb-7 胶囊）+ 24pt（有效期）= 132pt = 176px 勉强够 3 行但不够 4 行。用固定高度 + overflow-hidden 永远会在内容变动时炸，**Header 必须让内容自撑** |
| 32 | **pdfkit doc.text() 自动推进 doc.y 但不精确**：多行文本时 doc.y 会被 pdfkit 按字体行高自动推进，如果后面再加硬编码 `doc.y += 6` 就跳太多行 | **改 pdfkit 行距的正确做法**：统一用 `doc.moveDown(pt / 12)`（pdfkit moveDown 单位是 "lines"，一行 = fontSize × 1.2 ≈ 12pt），或者 doc.text 后传 `continued:false` 确保每次都新起一行。不要手动累加 doc.y |
| 33 | **后端 findChineseFont() 可能返回 null**：如果服务器上没有 CJK 字体，FONT_REG 会 fallback 到 Helvetica（西文字体不能渲染中文） | PDF 最终会是乱码，但 pdfkit 不会报错。**这个坑是后端部署环境层面的，不是代码层面**——如果未来 PDF 出现乱码，先 SSH 到服务器 `fc-list :lang=zh` 看有哪些中文字体 |
| 34 | **renderPdfItemsSection 的 ctx 参数可以不包含 SUB_DISPLAY_NAME**：v2 里 ctx 传过来的只有 `{ FONT_REG, FONT_BOLD }`，SUB_DISPLAY_NAME 函数内自己定义了一份（不是从 ctx 读的），前后端映射表**可能不一致** | feat/106 前后两次提交都改了 SUB_DISPLAY_NAME，要**同时查**前后端两处，不要只改一处（历史上 092/093 也出过类似问题：前端和后端 category 映射表有出入） |
| 35 | **Demo 模式的 `unit: '项'` Bug**：Demo Mock 数据里写了 `unit: '项'`，但真实后端 listPackageItems 返回的 item **没有 unit 字段**（字段里只有 quantity，不是 unit），所以只有 Demo 会出现"血脂6项 项"重复，真实数据不会 | **修 Demo 数据要按真实后端字段来**：真实后端没有 unit（只有 quantity 数量和 item_price 单价），Demo 也不应该有 unit。这和「Demo 模式的真实性」有关——Demo 字段越接近真实后端，线上越不容易出意外 |
| 36 | **亮点文案不要用项目总数做卖点**：129 是 3 个角色累加的，用户只会选 1 套做。数字类亮点容易被质疑凑数；行业通用卖点是「资质（三甲）+ 时效（7 天报告）+ 专属特色（两癌/PSA）」 | 体检行业套餐亮点**优先选非数字类**：资质背书、增值服务、专属特色、报告时效、医生资源，不要堆项目总数/分类数。数字只在"折扣力度"上出现才有意义 |
| 37 | **pdfkit addPage() 后自动保留上次 y 值**：`doc.addPage()` 会把 doc.y 保持在上一页底部（比如 750），但新页应该从顶部开始。所以 addPage 之后**必须显式**设 `doc.y = PAGE_TOP_AFTER_BREAK`，不然内容从页底继续渲染就乱了 | 所有调用 addPage 的地方后面必须跟 `doc.y = <页顶值>`，不能偷懒等 pdfkit 自动 |
| 38 | **Trae PowerShell profile 执行策略反复报 UnauthorizedAccess**：每次 RunCommand 都会在 stderr 看到 `File ... profile-snapshot.ps1 cannot be loaded because running scripts is disabled on this system`，但实际命令还是执行成功（这个 stderr 是 PowerShell profile 加载失败，不影响主命令） | **忽略这个 stderr 警告**，不用每次都去执行 `Set-ExecutionPolicy` 改策略（改了可能影响系统其他东西）。只要主命令 exit_code = 0 就行 |

### 8.9 踩坑教训（续 #38，新增 #39~#42）

| # | 踩坑 | 教训 |
|---|------|------|
| 39 | **migration race condition**：部署时 migrate 阶段还没跑到新列/新表，代码已经在用 → 报错阻塞用户 | 新列/新表的写操作必须 try/catch migration race（Unknown column / Table doesn't exist），静默降级不阻塞用户 |
| 40 | **authStore.isAdmin() 没复用 hasRole()** → roles 是对象数组时 `includes('admin')` 永远 false | isAdmin() 必须内部调用 hasRole('admin')，统一 roles 格式处理路径，不要自己另写一套 |
| 41 | **favicon 缓存顽固**：换了 favicon 但浏览器一直显示旧的 | 必须加 `?v=N` cache-busting 参数 + rebuild dist，且删除旧 .svg 文件避免 fallback |
| 42 | **签字 base64 PNG 进数据库 → sort_buffer 爆炸**：canvas 导出的未压缩 PNG 可以到几百 KB 甚至 MB 级 | 所有签字写入点必须做 size cap 校验（200KB），超限直接 400 返回前端 |

### 约束性内容

1. **feat/106 两个文件 + 4 个 commit** 未 push main，属于"开发中分支"，Gatekeeper 下次见到 `main..feat/106` diff 就是这批改动
2. **PDF 渲染分类排序**：SUB_ORDER 数组必须同步维护，新增 sub_category 时要往数组里加位置
3. **PDF 行距统一用 `doc.moveDown(pt/12)`**，禁止手动 `doc.y += N`
4. **pdfkit addPage 后必须显式设 `doc.y = PAGE_TOP_AFTER_BREAK`**
5. **renderPdfItemsSection 的高度常量 MAIN_LINE_H=12 / SUB_LINE_H=9 / CAT_TITLE_H=22 / CAT_BOTTOM_GAP=10 是预估和渲染的契约，改了必须两边一起改**

### 经验性内容

1. **前端 demo Mock 数据字段必须贴近真实后端 listPackageItems 返回结构**：后端 item 有 `item_name_snapshot / category / quantity / sub_item_names`，没有 `unit / sub_category`。Demo 里写了 unit 字段 → 出现"血脂6项 项"重复，就是字段不对齐的教训
2. **体检套餐亮点不要堆项目总数/分类数**，行业通用是资质背书 + 报告时效 + 角色专属特色
3. **pdfkit 不自动管分页时的内容不溢出**（不像 CSS），必须手动 estimateCategoryHeight + addPage 预判
4. **checkup-templates.js 的 PDF 路由有 2 条**：管理端 `/checkup-templates/:id/pdf`（需登录）+ 公开端 `/share/:token/pdf`（免登录），**分享 PDF 改 helper 两个路由都会受益**

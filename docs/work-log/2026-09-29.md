## 四、fix/192：扫码领料数量输入框支持小数

### 4.1 背景

仓库扫码领料页（`/scan-requisition`）购物车数量输入框无法输入 `0.25`，但 `1.25`、`2.25` 这种看起来"能输入"。用户实际是想按小数单位领料（如 0.25 kg / 0.5 瓶），但输入 `0.25` 后输入框直接消失。

### 4.2 根因

[src/pages/ScanRequisition/index.tsx#L529](file:///f:/OA/src/pages/ScanRequisition/index.tsx#L529) 购物车数量输入框用 `parseInt` 解析：

```tsx
onChange={(e) => setCartQty(item.item_id, parseInt(e.target.value) || 0)}
```

配合 `setCartQty` 中 `if (clamped === 0) return prev.filter(c => c.item_id !== itemId)`（0 就移除商品）：

| 输入 | `parseInt` | 后续 | 用户感受 |
|---|---|---|---|
| `0.25` | `0` | clamped=0 → 商品被移除 → 输入框消失 | "无法输入" |
| `1.25` | `1` | cartQty=1 → 受控 value 重渲染为 `"1"` | "能输入"（小数被吞未察觉） |
| `2.25` | `2` | 同上 | 同上 |

**后端实际支持小数**：[backend/routes/scan-requisition.js](file:///f:/OA/backend/routes/scan-requisition.js#L40-L48) 的 `toNum()` 用 `parseFloat`，DB `quantity` 字段也按 `Number()` 比较，整条链路都允许小数，只有前端这一行 `parseInt` 卡住。

### 4.3 为什么不能只把 parseInt 改成 parseFloat

直接换 `parseFloat` 仍会卡在受控组件 + 数字解析的经典坑（参考 [StockTakeOperate 盘点 H5](file:///f:/OA/src/pages/StockTakeOperate/index.tsx#L247) 已踩过的"尾部零被吞"问题）：

- 用户清空输入框 → `parseFloat("")` = `NaN` → `|| 0` → 0 → 商品被移除 → 没法继续输入
- 输入 `0.` 中间态 → `parseFloat("0.")` = `0` → 同上被移除
- 输入 `3.0` → 到 `3.` 时被重渲染回 `"3"`，再输 `0` 变 `30` 被库存 clamp，体验错乱

### 4.4 实现（commit `fb53c5c`，1 file，+35/-5）

**修改文件**：[src/pages/ScanRequisition/index.tsx](file:///f:/OA/src/pages/ScanRequisition/index.tsx)

复用盘点 H5 的 **draft 草稿字符串 + onBlur 提交** 模式：

1. **新增草稿状态**（[L64](file:///f:/OA/src/pages/ScanRequisition/index.tsx#L64)）：
   ```tsx

   ```

2. **输入框改为 draft 模式**（[L532-L555](file:///f:/OA/src/pages/ScanRequisition/index.tsx#L532-L555)）：
   - `type="number" step="any" inputMode="decimal"` 支持小数输入
   - `value` 优先取草稿字符串，回退到 `String(cartQty)`
   - `onChange` 只更新草稿 + `parseFloat` 给 setCartQty（NaN/负数兜底 0）

## 五、fix/193：预订确认H5按角色隐藏操作区

### 5.1 背景

销售员（如王艳艳）在 H5 预订确认单上签字确认后，订单状态变为 `reviewing`（待审核）。此时销售员再次打开该页面，仍看到签字栏和「驳回」「请先签字」按钮——这些实际是**审核员的操作区**，不应展示给销售员。

### 5.2 根因

H5 页面 [BookingConfirm/index.tsx](file:///f:/OA/src/pages/BookingConfirm/index.tsx) 渲染三个操作区（销售确认/审核/标记完成）时，**只判断了 `order.status`，没有判断"当前登录用户是否有权执行该操作"**：

```tsx
{order.status === 'sales_confirming' && ( 销售签字+确认按钮 )}
{order.status === 'reviewing'      && ( 审核签字+驳回/通过按钮 )}   // ← 销售员看到的就是这块
{order.status === 'confirmed'      && ( 完成签字+标记完成按钮 )}
```

只要订单处于 `reviewing` 状态，**任何人**打开都会看到审核员的签字栏和按钮。

而后端 [booking-board.js](file:///f:/OA/backend/routes/booking-board.js) 有权限校验（`isSalesOwnerOfOrder` / `isConfiguredBookingReviewer`），销售员真去点会返回 403，但前端 UI 不该把不属于她的操作展示出来。

### 5.3 对比：PC 端有过滤，H5 端缺失

PC 端 [BookingBoard/index.tsx](file:///f:/OA/src/pages/BookingBoard/index.tsx) 有完整的身份过滤：

```tsx
const canSalesConfirm = isOrderSalesPerson;
const canReviewOrComplete = isConfiguredReviewer;
{order.status === 'sales_confirming' && canSalesConfirm && (...)}
{order.status === 'reviewing'      && canReviewOrComplete && (...)}
```

H5 端的 `BookingConfirm` 没有这段逻辑，导致越权展示操作 UI。

### 5.4 实现（commit `c87f530`，2 files，+37/-4）

**修改文件**：
- [src/lib/api.ts](file:///f:/OA/src/lib/api.ts)
- [src/pages/BookingConfirm/index.tsx](file:///f:/OA/src/pages/BookingConfirm/index.tsx)

#### 5.4.1 api.ts：补全 bookingApprover 配置字段

后端 `/booking/config` 早已返回 `bookingApprover`（企微配置的预订审核员 userid + 姓名），但前端 `BookingConfig` 接口和 `getConfig()` 映射漏掉了这个字段。

- `getConfig()` 映射加 `bookingApprover: d.bookingApprover || d.booking_approver || null`

#### 5.4.2 BookingConfirm：加角色守卫

新增两个身份判断（对齐 PC BookingBoard + 后端规则）：

| 判断 | 逻辑 | 对应后端函数 |

| `isOrderSalesPerson` | 当前用户 id / wecom_userid / 姓名 与订单的 `salesPersonId` / `salesWecomUserid` / `salesPerson` 任一匹配 | `isSalesOwnerOfOrder` |

## 六、踩坑教训 & 经验

1. **未鉴权接口 = 定时炸弹**（ref：fix/190，2026-09-29）：wecom.js 整文件没有导入 `requireAuth`，6 个写/发送接口全裸奔。攻击者 0 成本调用。**任何写操作、发送消息、修改配置、改密码的接口必须加 `requireAuth`，敏感操作再加 `requireRole`。**

2. **SSRF 用白名单比黑名单好**（ref：fix/190，2026-09-29）：攻击者把 `test_webhook_url` 改成 `http://169.254.169.254/latest/meta-data/` 读云元数据。黑名单要维护所有内网 IP 段且 DNS rebinding 可绕，白名单只允许 `https://qyapi.weixin.qq.com/` 简单可靠。**对外发起 HTTP 请求的 URL 配置一律用域名白名单。**

3. **改密接口必须用 req.user.id，不能信前端 userId**（ref：fix/190，2026-09-29）：`/change-password` 接收 `userId` 参数，攻击者可遍历 id 改任意人密码。**所有"修改当前用户数据"的接口都用 `req.user.id`，忽略前端传的 id。**

4. **登录接口要做类型校验**（ref：fix/190，2026-09-29）：`username: 0` 被某些 ORM/驱动当作通配匹配，可能匹配到 admin。**username/password 必须 `typeof === 'string'` 且非空，再做后续查询。**

5. **登录页不要硬编码密码**（ref：fix/190，2026-09-29）：默认密码 `admin123` / `viewer123` 写在前端代码里，等于公开。**前端代码不应包含任何密码字面量，体验账号密码私下告知。**

6. **生产环境快速登录只能填用户名**（ref：fix/191，2026-09-29）：fix/190 用 DEV 守卫把快速登录完全藏起来后，用户觉得体验下降。折中方案：保留"查看员账号"按钮，但只填用户名不填密码，密码必须手输。这样既方便又不暴露密码。**admin 等敏感账号不应有快速入口。**

7. **入侵响应要先止血再修代码**（ref：fix/190，2026-09-29）：本次先在服务器侧手动重置 admin 密码 + 清空恶意 URL，让系统恢复登录，再走完整的代码修复流程。**紧急情况先保证可用性，再做根治。**

8. **受控数字输入框禁用 parseInt，小数场景用 draft 草稿 + onBlur 模式**（ref：fix/192，2026-09-29）：扫码领料数量输入框用 `parseInt` 把 `0.25` 截成 `0`，配合 `setCartQty` 中 `clamped === 0` 移除商品的逻辑，直接把商品从购物车移除，输入框消失，用户感受是"无法输入 0.25"；而 `1.25`/`2.25` 被截成 `1`/`2` 后受控 value 重渲染为 `"1"`/`"2"`，用户感觉"能输入"但小数实际被吞。**只把 parseInt 换 parseFloat 不够稳**——清空、`0.` 中间态、`3.0` 尾零都会被 Number→String 重渲染吞掉。正确模式：草稿字符串 state 保存用户原始输入，onChange 只更新草稿 + parseFloat 解析给业务 state，onBlur 清除草稿回落到 `String(value)`，参考 [StockTakeOperate](file:///f:/OA/src/pages/StockTakeOperate/index.tsx#L247)。**凡是受控数字输入框且 value 由 Number 重渲染来的，都要走 draft 模式。**

9. **setCartQty 不要在 0 时立即移除商品**（ref：fix/192，2026-09-29）：用户输入小数中间态（如 `0.`、`0.2`）时 parseFloat 会得到 0，如果此时立即 `prev.filter` 移除商品，输入框直接消失没法继续输。**0 时不再新增，但已在购物车的保留**，提交时再统一过滤 `cartQty<=0` 的项，既不卡中间态也不会误提交 0 数量。

10. **H5 操作区渲染不能只看 order.status，必须同时校验当前用户角色**（ref：fix/193，2026-09-29）：BookingConfirm H5 三个操作区（销售确认/审核/标记完成）只判断 `order.status` 不判断当前用户身份，导致销售员确认后（status=reviewing）仍看到审核员的签字栏和按钮。PC 端 BookingBoard 有 `canSalesConfirm`/`canReviewOrComplete` 身份过滤，H5 端却缺失。**凡是同一业务有 PC 和 H5 两端的前端，角色过滤逻辑必须同步，不能只在一端做。** 后端有权限校验（会返回 403），但前端 UI 不应展示不属于当前用户的操作入口。

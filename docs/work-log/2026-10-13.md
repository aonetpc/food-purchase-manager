### 1.3 feat/209：用户实测反馈两个问题（commit `0e6875c`，merge `075ae76`）

#### 问题一根因：`isAdmin` 是函数，被当成布尔值使用导致条件恒真

[src/store/authStore.ts](../../src/store/authStore.ts) 中 `isAdmin` 定义为 store action（函数）：

```ts
isAdmin: () => get().hasRole('admin'),   // 类型是 () => boolean，不是 boolean
```

而页面沿用文件里既有写法，解构后直接当布尔值用：

```ts
const { isAdmin, user } = useAuthStore();
{isAdmin && (...)}   // 函数对象恒为真 → 所有用户都能看到管理功能
```

该文件此前已有 **3 处相同的旧误用**，首版新增代码复制沿用，共 5 处受影响：

| 位置 | 错误表现 | 实际后果 |
|------|----------|----------|
| 采购员筛选下拉（feat/208 新增） | 恒为真 | 非管理员也显示筛选框（用户反馈） |
| 加载用户列表 useEffect | 恒为真 | 非管理员也在调用户接口 |
| 已收货/确认单删除按钮 | 恒为真 | 非管理员也显示删除按钮（后端会拒绝，但 UI 误导） |
| 审批中撤回按钮 `!isAdmin` | **恒为假** | 撤回按钮对所有人都不显示（隐藏的真 Bug） |
| 草稿删除按钮 `(isAdmin \|\| created_by===uid)` | 恒为真 | 无实际影响（非管理员只能看到自己的单） |

修复：组件顶部取一次真实布尔值，5 处统一替换：

```ts
const isAdminUser = isAdmin();
```

顺带修复"撤回按钮不显示""非管理员显示删除按钮"两个历史遗留 Bug。

#### 问题二根因与修复：下拉数据源换成"实际有采购单的人"

首版数据源是全量系统用户 `/auth/users`，含从未下过采购单的管理员、查看角色。

新增后端接口 [warehouse-purchases.js#L1551](../../backend/routes/warehouse-purchases.js#L1551)：

```sql
SELECT wp.created_by AS id,
       COALESCE(MAX(NULLIF(u.name, '')),
                MAX(NULLIF(wp.created_by_name, '')),
                wp.created_by) AS name
FROM warehouse_purchases wp
LEFT JOIN users u ON u.id = wp.created_by
WHERE wp.created_by IS NOT NULL AND wp.created_by != ''
GROUP BY wp.created_by
ORDER BY name ASC
```

- 只返回**实际创建过采购单的用户**（含历史离职人员，保证能按人筛历史订单）；
- 姓名优先取 users 表最新值（改名后下拉显示新名字），用户被删时兜底取采购单冗余的 `created_by_name`；
- 接口加 `requireAuth` + admin 角色校验，非管理员直调返回 403；
- 注册在 `GET /:id` 之前（静态路径段必须先于动态参数路由，否则被 `/:id` 拦截）；
- 前端数据源从 `/auth/users` 换成 `/warehouse-purchases/purchasers`。

## 三、关键决策记录

### 3.1 筛选权限在后端硬隔离，前端只做显示控制

非管理员分支直接硬编码 `created_by = req.user.id`，前端传任何 `created_by` 都被忽略。前端 `isAdminUser` 控制下拉渲染只是体验层，真正的安全边界在后端。独立的 `/purchasers` 筛选项接口本身也做 admin 校验兜底——即使前端判断再出漏洞，非管理员也拿不到全量采购员名单。

### 3.2 筛选项列表从业务数据 DISTINCT 派生，而非全量用户表

对比过三个方案：① 新增接口从采购单 `DISTINCT created_by` 派生（采纳）；② 下拉加搜索框（暂缓，采购员数量不多时没必要）；③ 前端按角色过滤全量用户（否决：需硬编码角色枚举、漏历史人员、列表仍长）。方案①从数据层根治——没下过单的人天然不出现，离职人员仍可筛历史订单，且姓名 JOIN users 取最新值。

### 3.3 isAdmin 修复采用"组件顶部取布尔值"而非逐处调用

`const isAdminUser = isAdmin()` 在组件体顶部执行一次，所有 JSX 条件统一用布尔变量，避免 5 处分别调用的重复与渲染期函数调用，也与文件内 `user?.id` 等派生值风格一致。

## 五、踩坑教训

1. **Zustand store 的 action（函数）解构后不能当布尔值用**（ref：feat/209，2026-10-13）：`isAdmin` 在 store 里类型是 `() => boolean`，`const { isAdmin } = useAuthStore()` 拿到的是函数引用，`{isAdmin && ...}` 恒真。使用 store 字段做条件前必须核对类型定义：函数要先调用 `isAdmin()` 取布尔值。排查信号：某条件 UI"所有角色都能看到/都看不到"且条件写的是 store 解构变量 → 先查该字段是不是函数。

2. **恒真/恒假权限条件会同时产生两个方向的 Bug，排查必须列全影响面**（ref：feat/209，2026-10-13）：`isAdmin &&` 恒真导致越权显示（筛选框、删除按钮），而同一变量的 `!isAdmin &&` 恒假导致合法功能永久消失（撤回按钮）。修复时必须 grep 该变量的**全部出现位置**逐一核对，不能只修用户截图反馈的那一处——本次一次性修了 5 处，其中 2 处是用户未发现的历史遗留 Bug。

3. **新增代码复制"文件内既有写法"前要验证写法本身是否正确**（ref：feat/209，2026-10-13）：首版筛选下拉的 `isAdmin` 误用直接沿用了同文件 3 处旧代码的错误模式，说明"现有代码就这么写"不代表写法正确。涉及权限/鉴权的既有模式应回到 store/类型定义处确认，而不是就近复制。

4. **筛选器/下拉的选项数据源应从业务数据派生，不要默认用全量基础表**（ref：feat/208→209，2026-10-13）："按 X 筛选"的选项列表 = 业务表里实际出现过的 X（DISTINCT 业务外键 JOIN 名称表），而非 X 的全量主数据。全量主数据会混入从未发生业务的实体（系统管理员）、随组织膨胀变长、还可能泄露不该出现的人员。姓名展示用 COALESCE 取主表最新值、业务表冗余值兜底，兼顾改名与删除。

5. **Express 静态路由段必须注册在 `/:id` 动态路由之前**（ref：feat/209，2026-10-13）：新增 `GET /purchasers` 若写在 `GET /:id` 之后，请求会被 `/:id` 捕获并把 `"purchasers"` 当订单 ID 查询。新增同层静态路径时固定动作：grep 路由文件中 `router.get('/:xxx'` 的位置，确保静态段在前（文件内 /confirm-page 已有同样注释约定）。

6. **本机 github.com:443 连接超时是环境网络问题，不是仓库/凭证问题**（ref：2026-10-12、10-13 连续两天）：报错 `Failed to connect to github.com port 443 after 210xx ms: Could not connect to server`，fetch/push 均失败，git 无代理配置。处置：本地照常分支提交 + 合并 main，push 留待网络恢复（代理/VPN）后一次推齐；不反复空转重试。

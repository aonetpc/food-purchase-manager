## 五、出错教训/踩坑记录（供未来规避）

| # | 踩坑点 | 教训 |
|---|--------|------|
| 1 | 前端读错后端字段名 → `sid = supplier.id` vs 后端 `supplier_id`；`pending_count` vs `purchase_count`；`pending_amount` vs `total_amount` | **新增后端接口后，前后端字段名必须逐行对齐**，建议用 API 类型共享（OpenAPI / shared.ts interface）避免字段名拼写不一致 |
| 2 | SQL 引用不存在的列 `purchase_date`（实际存 `created_at`）导致展开接口 500 | **写后端 SQL 前必须对照迁移脚本的列名**，或用后端 IDE 的 schema 智能提示，不要凭记忆猜列名 |
| 3 | authStore 里"所有用户可见"兜底绕开 RBAC，功能上线时没补 migration 权限 → 所有用户都能看到菜单 | **任何新增菜单必须先写迁移在 permissions 表注册 + 角色关联，再删掉前端兜底注入**，兜底只能作为 migration 生效前的临时措施 |
| 4 | 多条修复 commit 混在 main 分支 → Gatekeeper 推送时容易夹带 | **每个独立修复功能必须从 main 切独立 feature/fix 分支再 commit**，避免多条业务线搅在一起无法独立开 PR |
| 5 | **confirmed 状态订单编辑报错 `Unknown column 'confirmed_by'`**：后端把审核通过确认人字段 `approved_by` 错写成不存在的 `confirmed_by` | **涉及状态流转的降级/晋级 SQL，先 grep 迁移文件找到真实列名**（approved_by vs confirmed_by vs sales_confirmed_by 语义非常容易混），不要按状态名直接猜列名 |
| 6 | **"已确认"标签对应 2 个后端状态（confirmed / completed），列表卡片点击处理成统一编辑**，导致 completed 订单（后端 EDITABLE_STATUS 不包含）编辑保存报 400 | **UI 状态（DisplayStatus）与后端状态（OrderStatus）必须 1:1 判定分支**，展示态合并显示是可以的，但操作按钮/点击行为不能只看展示态，要回到后端枚举值做判断 |
| 7 | PowerShell git commit heredoc / 多行 `-m` 的 `()` 和空格解析报错 | Windows PowerShell 环境下 git commit 消息优先用简单单行 `-m "..."`，不要用 bash heredoc；多段 `-m` 时避免消息里含括号 `( )` 和冒号 `:`，否则被 PS 当参数解析 |

## 三、关键决策记录

### 3.1 入库时间放头部第 2 行，与签字区确认时间并存

头部承担单据概览（采购单号/仓库/供应商/金额/状态/**入库时间**），签字区承担流程留痕（确认人/确认时间）。收货节点与确认节点是两个独立业务时间，截图实证可相差 1 小时，不互相替代。

### 3.2 数据源直接复用 feat/215 派生口径，零新字段

确认单 PDF 的入库时间与 OA 详情、出入库记录页同源——同一条 `MIN(created_at)` 派生 SQL，保证三个界面数字永远一致；不新建 `received_at` 列，无迁移、无回填问题。

### 3.3 老单缓存 PDF 不批量重生成

下载接口对已有缓存文件直接返回，不主动重生成；批量刷新历史 PDF 文件没有必要（老单少有人再下载），按需点「生成确认单」即可覆盖缓存，零脚本零风险。

### 3.4 申请单 PDF 不加入库时间

申请单在收货前生成，加了永远是 `-` 空列；单据各有信息边界——申请单管「该不该买」（feat/216 加了申报库存），确认单管「什么时候入的库」。

## 五、踩坑教训

1. **同名 PDF 缓存文件要排查全部生成时机再下结论**（ref：feat/217，2026-10-19）：确认单 PDF 有 3 条生成路径（自动确认、手动按钮、下载兜底），排查时先 grep 全部调用点确认「都发生在收货之后」，才能放心在 PDF 函数里用收货流水派生——漏看一条路径就可能生成空值 PDF。固定动作：`Grep "generateXxxPDF"` 数全调用点，逐点核对业务时序。

2. **「某字段已在别处展示」≠「所有输出物都有」**（ref：feat/217，2026-10-19）：入库时间 feat/215 只加了 OA 详情页，PDF 是独立渲染链路（pdfkit 手工排版），不会自动继承。凡同一信息需要在「网页 + PDF + 企微消息」多载体展示时，必须逐载体核对——三类载体三套渲染代码，互不相通。

3. **push 输出中的 remote 提示信息要与 ref 更新行区分**（ref：feat/217 推送，2026-10-19）：GitHub 在 push 成功时也可能输出 `remote: Changes must be made through a pull request.` 之类的提示文案，判断推送是否成功只看 ref 行（`65e4b6f..7e227da main -> main`），并用 `git log origin/main -1` + `git log origin/main..main` 二次核实，不被提示文案误导重试。

4. **同一派生口径多处使用时，复制 SQL 必须连同注释里的坑一起带走**（ref：feat/217，2026-10-19）：`movement_type='inbound'` 过滤条件在 feat/215 详情接口里已注明「即采即用会同时写 inbound+expense 两条流水」，feat/217 复制到 PDF 函数时注释一并保留——后来者只拷 SQL 不拷注释，下次再有人复用就可能丢掉过滤条件。

5. **小改动也要完整走完「分支→安全检查→合并→推送」流程**（ref：feat/217，2026-10-19）：本次仅 +17/-1 单文件，但流程不省略——安全检查通过按约定直接合并推送，用户零等待；流程的价值在于一致性而非改动大小。

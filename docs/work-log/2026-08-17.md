### 1. 新建套餐页面模板卡片三角色胶囊颜色丢失修复（P1）

- **问题**：新建套餐页面（WizardNew）下方"模板卡片底部价格胶囊 / 角色价格徽章"三角色全部显示为灰色无边框，没有蓝/粉/紫的区分色。

  ```tsx
  // 胶囊配色：模板卡片底部价格胶囊 / 角色价格徽章
  const ROLE_CAPSULE: Record<Role, string> = {
    male:             'bg-blue-50   border-blue-100 text-blue-800',
    female_married:   'bg-pink-50   border-pink-100 text-pink-700',
    female_single:    'bg-purple-50 border-purple-100 text-purple-800',
  };
  ```
- **涉及文件**：
  - [WizardNew.tsx](file:///workspace/src/pages/CheckupTemplates/WizardNew.tsx) — 新增 ROLE_CAPSULE 映射 + 模板卡片下方胶囊 className 应用

### 3. 我的套餐列表金额显示 ¥0 修复（P3）

- **问题**：用户反馈"我的套餐"列表页所有套餐的角色金额都显示为 ¥0，但点进去套餐详情里的项目价格是有的。
- **根因（双重）**：

  | # | 层级 | 问题 | 影响 |
  |---|------|------|------|
  | 1 | 后端克隆接口 | 08-16 修复 P2 时，把克隆 `role_plans` 改为清零（`original_total=0, discount_price=0, discount_rate=100`），原意是让后续 `items-batch` 重算。但**克隆后用户直接关闭页面没有点保存**（即未触发 items-batch），role_plans 就一直是 0 | 克隆出来的套餐在列表页显示 ¥0 |
  | 2 | 后端列表接口 | `GET /` 列表接口只读 `role_plans.discount_price` 字段，没有从 items 快照兜底重算 | 即使 role_plans 是 0，列表也没有兜底 → 显示 ¥0 |

- **修复方案（双保险）**：

  **P3-后端克隆接口（即时重算）** [checkup-templates.js POST /:id/clone](file:///workspace/backend/routes/checkup-templates.js)：
  ```js
  // 克隆 role_plans：按刚克隆出来的项目快照即时重算三角色价格（含保险价）
  const roleTotals = { male: 0, female_married: 0, female_single: 0 };
  for (const it of srcItems) {
    const amt = (toNum(it.item_price) + toNum(it.insurance_price_snapshot)) * Math.max(1, toNum(it.quantity) || 1);
    if (it.role === 'common') {
      for (const r of ROLES) roleTotals[r] += amt;
    } else if (roleTotals[it.role] !== undefined) {
      roleTotals[it.role] += amt;
    }
  }
  for (const r of ROLES) {
    const total = round2(roleTotals[r]);
    await conn.query(
      `INSERT INTO booking_package_role_plans (id, package_id, role, original_total, discount_price, discount_rate)
       VALUES (?, ?, ?, ?, ?, 100)`,
      [uuidv4(), newId, r, total, total]
    );
  }
  ```
  📌 **关键点**：克隆时**不依赖用户后续是否点保存**，立即按源套餐的项目快照算出三角色总价，`original_total = discount_price = total`（不打折，rate=100），保证克隆完即可见正确价格。

  **P3-后端列表接口（兜底计算）** [checkup-templates.js GET /](file:///workspace/backend/routes/checkup-templates.js)：
  ```js
  // ========== 兜底：对 role_plans.price=0 的套餐，从 items 快照临算，避免 ListPage 显示 ¥0 ==========
  const fallbackPids = [];
  for (const [pid, plans] of plansMap.entries()) {
    for (const r of ROLES) {
      const pl = plans[r];
      if (!pl || Number(pl.discount_price) === 0) { fallbackPids.push(pid); break; }
    }
  }
  if (fallbackPids.length > 0) {
    const [itemsRows] = await pool.query(
      `SELECT package_id, role, item_price, insurance_price_snapshot, quantity
       FROM booking_package_items
       WHERE package_id IN (${fallbackPids.map(() => '?').join(',')})`,
      fallbackPids
    );
    // ... 聚合并回填 plansMap
  }
  ```
  📌 **关键点**：列表接口对历史遗留的 ¥0 套餐（包括 08-16 清零策略产生的、或更早克隆逻辑产生的）自动从 items 快照重算，无需手动跑修复脚本。

## 二、易错点 & 必须牢记的细节（重点回顾）

### ⚠️ 易错点1：JavaScript 后端文件中误用 TypeScript 语法（昨日新踩坑）

[checkup-templates.js](file:///workspace/backend/routes/checkup-templates.js) 是 `.js` 文件，**不能用 TypeScript 类型注解**。

📌 **错误示例**（昨日 Bug）：
```js
const fallbackPids: string[] = [];        // ❌ :string[] 是 TS 语法
const byPkg = new Map<string, any[]>();    // ❌ Map<string, any[]> 是 TS 泛型语法
```

📌 **正确写法**：
```js
const fallbackPids = [];                  // ✅
const byPkg = new Map();                  // ✅
```

📌 **教训**：
1. 后端 Node.js 项目走 CommonJS，`.js` 文件**不带类型系统**，写 TS 注解会直接报 `SyntaxError: Unexpected token ':'`，整个路由文件加载失败
2. 复制粘贴前端 `.tsx` 代码片段到后端 `.js` 文件时，必须**手动剥离所有类型注解**
3. 自检命令：`node -c backend/routes/checkup-templates.js` 可以在部署前快速检查语法

### ⚠️ 易错点2：React 组件作用域 — 函数定义位置（昨日新踩坑）

[WizardItems.tsx](file:///workspace/src/pages/CheckupTemplates/WizardItems.tsx) 的 `ItemCard` 子组件声明在文件顶层（在 `WizardItems` 函数外），但它调用的 `getApplicableLabel / scopeVisible` 函数却被定义在 `WizardItems` 函数体内（闭包内）→ 跨作用域引用失败。

📌 **错误结构**：
```tsx
export default function WizardItems() {
  function scopeVisible(...) { ... }      // ❌ 闭包内
  function getApplicableLabel(...) { ... } // ❌ 闭包内
  // ...
}

function ItemCard({ it, ... }) {           // 在 WizardItems 外，访问不到上面的函数
  const label = getApplicableLabel(it);    // ❌ ReferenceError
  // ...
}
```

📌 **正确结构**（昨日修复后）：
```tsx
const EMPTY_SCOPE = { ... };

function scopeVisible(...) { ... }         // ✅ 文件顶层
function getApplicableLabel(...) { ... }    // ✅ 文件顶层

export default function WizardItems() { ... }

function ItemCard({ it, ... }) {            // 与上面两个函数同作用域
  const label = getApplicableLabel(it);     // ✅
}
```

📌 **规则**：
1. **被多个组件共享的纯函数**（无 state、无 hooks）应该提到**文件顶层**或独立的 utils 文件，不要藏在某个组件闭包里
2. 判断标准：如果一个函数**没有引用任何组件内部的 state/props/hooks**，就应该是文件顶层函数
3. React 的 React Fast Refresh 也会因为闭包内的函数热更新失效而踩坑，提到顶层还能让 HMR 更稳定

### ⚠️ 易错点3：Tailwind 动态 class 的 JIT 陷阱（昨日新踩坑）

Tailwind JIT 扫描源码时，**class 名必须是字面量字符串**，不能由变量拼接。

📌 **错误示例**：
```tsx
const color = 'blue';
<div className={`bg-${color}-50`} />      // ❌ JIT 扫描不到 bg-blue-50，不生成 CSS
```

📌 **正确写法**：把完整 class 名写在映射表里
```tsx
const ROLE_CAPSULE = {
  male: 'bg-blue-50 border-blue-100 text-blue-800',  // ✅ 完整字面量
  // ...
};
<div className={ROLE_CAPSULE[role]} />     // ✅ JIT 能扫描到
```

📌 **教训**：
1. **任何「按角色/类型区分颜色」的 UI**，都要建立 `Record<Role, string>` 的**完整 class 映射表**
2. 不同 UI 场景（卡片边框 vs Tab 选中态 vs 胶囊背景）应该建**独立的映射表**（如 `ROLE_STYLE` / `TAB_ROLE_STYLE` / `ROLE_CAPSULE`），不要复用同一张表 —— 否则改一处影响多处，且颜色深浅需求不同（边框浅、选中深）
3. 映射表的 class 字符串里**多余的空格不影响**，但每个 class 必须是 Tailwind 字典里真实存在的

### ⚠️ 易错点4：克隆套餐 role_plans 的策略演变（重要决策回顾）

08-16 和 08-17 两个版本对克隆 `role_plans` 的策略**完全相反**，这里记录演变过程：

| 日期 | 策略 | 原因 | 后果 |
|------|------|------|------|
| 08-16 | **清零**（original_total=0, discount_price=0, rate=100） | 担心继承原模板价格导致"僵尸价"，依赖后续 items-batch 重算 | 用户克隆后**不点保存**就关闭，role_plans 一直是 0 → 列表显示 ¥0 |
| 08-17 | **即时重算**（按 srcItems 快照算三角色总价） | 修复 08-16 的 ¥0 Bug，且后续 items-batch 还会再算一次（幂等） | 克隆完即可见正确价，items-batch 重算也不会出错 |

📌 **最终结论**（08-17）：
1. **克隆时必须即时重算**，不能依赖"用户后续会触发重算"
2. 用户的行为不可预测（可能关闭页面、可能断网、可能刷新），所有 INSERT 类型的克隆接口都应该**把派生数据算好再写库**
3. 列表/详情接口的**兜底计算**是第二道保险，覆盖历史遗留数据和意外情况
4. `items-batch` 重算接口仍然保留，是用户修改项目时的核心重算入口

### ⚠️ 易错点5：role_plans 价格计算的"common 分摊"逻辑（反复使用，必须记牢）

三角色价格的聚合规则——一个项目如果是 `role='common'`，它的金额会**分摊到三个角色**；如果是单独角色，只加到那个角色。

📌 **代码模板**（克隆接口、列表兜底、items-batch 重算都用到）：
```js
const roleTotals = { male: 0, female_married: 0, female_single: 0 };
for (const it of items) {
  const amt = (toNum(it.item_price) + toNum(it.insurance_price_snapshot)) * Math.max(1, toNum(it.quantity) || 1);
  if (it.role === 'common') {
    for (const r of ROLES) roleTotals[r] += amt;   // ✅ 三个角色都加
  } else if (roleTotals[it.role] !== undefined) {
    roleTotals[it.role] += amt;                     // ✅ 只加到对应角色
  }
}
```

📌 **易错点**：
1. `quantity` 默认为 1（`Math.max(1, toNum(it.quantity) || 1)`），不能直接用 `quantity`（可能是 null/undefined/0）
2. `item_price + insurance_price_snapshot` 两个价格都要算（保险价是叠加在项目价上的）
3. `it.role === 'common'` 判断要放在 `roleTotals[it.role]` 之前，否则 common 会漏算
4. `round2()` 最后调用，不要在循环内调（性能浪费）

## 三、关键决策记录

### 决策 1：克隆 role_plans 改为「即时重算」而非「清零」（08-16 决策的反转）

- **选择**：克隆时按 srcItems 快照**立即计算三角色总价**，写入 `original_total = discount_price = total, rate=100`
- **原因**：
  1. 08-16 的清零策略依赖"用户后续点保存触发 items-batch 重算"，但用户行为不可控
  2. 即时重算后，items-batch 后续仍然会重算（幂等），不会冲突
  3. 列表接口的兜底计算是第二道保险，但克隆接口自己算好才是根本

### 决策 2：Tailwind 配色映射按「UI 场景」独立分表

- **选择**：`ROLE_STYLE`（卡片整体）、`TAB_ROLE_STYLE`（Tab 选中态 + 底部胶囊）、`ROLE_CAPSULE`（模板卡片胶囊）三张表独立
- **原因**：
  1. 不同 UI 场景对颜色深浅需求不同（边框浅、选中态深）
  2. 复用同一张表会改一处影响多处，且不一定满足所有场景
  3. 独立分表后，每个场景可以单独调整，互不影响

### 决策 3：列表接口兜底计算只对 ¥0 套餐触发（避免每次列表都重算）

- **选择**：列表接口先扫描 `role_plans.discount_price === 0` 的套餐，只对这些套餐从 items 重算
- **原因**：
  1. 全量重算会让列表接口变慢（套餐数量多时尤其明显）
  2. ¥0 是异常状态（克隆清零策略或历史遗留产生的），正常套餐都有价格
  3. 兜底计算是"修复"性质，不是"日常计算"，只对异常数据触发即可

## 二、三轮核心修复（用户反馈驱动）

### 2.1 第一轮：用户指出3处问题

| # | 问题 | 诊断 |
|---|------|------|
| 1 | 已入库订单少了很多 | 当前 `NOT IN ('draft','cancelled')` 把审批中/审批通过未入库/被拒绝的也算了，反而漏了真正已入库的 |
| 2 | 分类只显示 L1 大类 | `warehouse_items.category_id` 存的是 L3，当前只 JOIN 到 L1，丢了 L2 |
| 3 | 「未指定供应商」是什么？ | 截图里 ¥336.40 混了两种数据：临时供应商（supplier_name 有值但 supplier_id 空）+ normal 类型（两者都空） |

### 2.2 第二轮：用户补充「临时供应商应归现有供应商；已入库订单都要统计」

**供应商分组策略**（三级 group_key）：
- `supplier_id` 有值 → 真实供应商，关联 `suppliers` 表取标准名
- `supplier_name` 有值但 `supplier_id` 空 → 临时供应商，加 `temp:` 前缀独立成行
- 两者都空 → `none`，归「无供应商采购」（normal 类型）

**分类层级修复**：多 JOIN 一层取 L2 的父级作为 L1，展示 `CONCAT(wc_l1.name, '·', wc_l2.name)` 如「原材料·绿化工程类」

### 2.3 第三轮：运行报错 `Unknown column 'wp.inbound_no'`

**根因**：我在第二轮方案里猜了一个**不存在的字段** `wp.inbound_no`。warehouse_purchases 表（迁移 034 L112-138）根本没有这个字段，后续 037/046/048 也没加过。

**正确判定**（参考 [warehouse-purchases.js L3179](file:///f:/OA/backend/routes/warehouse-purchases.js#L3179) 冲回库存逻辑）：
```sql
-- 错误
WHERE wp.inbound_no IS NOT NULL AND wp.inbound_no <> ''

-- 正确
WHERE wp.status IN ('received','confirming','confirmed','reimbursing','reimbursed')
```

入库流水实际存在 `stock_movements` 表（`movement_type='inbound', related_type='purchase', related_id=wp.id`），与 status 状态在同一事务写入，一一对应，用 status 判定更简洁。

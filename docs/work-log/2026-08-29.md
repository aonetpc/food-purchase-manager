### 2.2 分支管理规则（落地）
- **分支命名**：`feat/NNN-<功能简称>` 或 `fix/NNN-<bug简称>`（NNN 为 3 位自增编号），禁止无编号模糊命名（如 `test-xxx` / `my-branch`）
- **main 不直接 commit**：功能一律落到 feat/fix 分支，由 Gatekeeper 合并；已有的脏 commit 用「reset hard + cherry-pick」流程清理（昨日实际执行 1 次成功）
- **永远不要合并的分支**：`fix/booking-delete-admin-and-click-date`（tip db4a359）是旧版本快照，合并会把后续的变更单流程/报表改造/体检权限/103~105 迁移等全部回退。**Gatekeeper 铁律：看到该分支立刻打回，不允许合入**
- **功能对话必须先 COMMIT 才能合入**：feat/093 昨天最初脏改动在工作区未 commit（分支 tip 0 个提交），Gatekeeper 先帮它 commit（c39106a）再合并，避免合并后丢失未 commit 代码
- **Owner 两条推送路径并存**：① 规范路径（Gatekeeper 预审 → 合并 main → 你 push）；② 功能对话直接 push（Owner 绕过）。路径 ② 没有预审，所以每天 Gatekeeper 必须做一次「origin/main 近 3 个 commit diff 盘点」检查是否有夹带回退

## 六、出错教训/踩坑记录（续 #19~#27，接上篇 #8~#18）

| # | 踩坑点 | 教训 |
|---|--------|------|
| 19 | **Branch Protection「Include administrators + 强制 ci-check status」会拦 Owner 直推**：勾了这两项，`git push origin main` 直接 GH006 rejected，每次部署都得去 Settings 开关 1 次 → 浪费时间 | 永久解：取消 Require status checks + Include admin 不勾（我们选的）。**记住：不要手贱把 status checks 再勾回来** |
| 20 | **bat 文件（cmd.exe）不能写中文**：UTF-8 存的中文在代码页 936 里变乱码，乱码内容又被 cmd 当命令解析 → 出现 "'it' 不是内部命令"、乱码伪命令等莫名其妙报错 | push-deploy.bat 必须纯英文 ASCII（注释、报错提示全英文）；要写中文提示就换 PowerShell 脚本（.ps1），.ps1 默认 UTF-8 不炸 |
| 21 | **功能对话「脏改动在工作区但没 commit」= 分支 tip 0 个提交**：feat/093 出现过，导致第一次扫描"0 领先 main"以为没东西可合，实际代码就写在工作区 | Gatekeeper 预审流程加一步：检查每个 feat/fix 分支 `git status --short`，若出现 M/?? 且 diff 是实际改动，先帮功能对话 `git add && git commit`（写好 commit message）再合 |
| 22 | **功能对话可以「自己合并自己 push」绕过 Gatekeeper**（Owner 绕过保护打开）：昨日 64a48f3 合并后 push 到 main（74752d3）是另一个对话直接做的，导致我们没来得及审查 diff，差点把 reports.js 大量删除（回退 feat/093）带进 main | 两条防线：① 每天 Gatekeeper 做一次「origin/main tip 的 2-3 个 commit 内容盘点」，确认 diff 没有回退代码；② 功能对话启动词明确写"不要自己上传"，但 AI 100% 遵守无法保证（Branch Protection 无法区分是你本人还是 TRAE 对话推的，都是 Owner 身份） |
| 23 | **分支 tip 上挂「其它模块代码回退」非常危险**：fix/092 最新提交 64a48f3 的提交信息写「恢复菜单兜底 + 滚动修复」，但 diff 里却有 reports.js + ManagementReport（报表模块文件）356 行删除，等于回退 feat/093。这种"挂羊头卖狗肉"的 commit 靠提交信息完全看不出 | **Gatekeeper 必做步骤**：合并前必须看 `git diff --stat main..<branch>` 的文件列表，核对「改动的文件是不是这个分支编号范围的模块」，跨模块大删一律打回 |
| 24 | **两个功能对话同时修改 main 会导致「本地落后远端」push 失败**：昨日发生两次「本对话合并完 → 还没 push → 另一个对话已经 push 了别的 commit」→ 本对话 push 显示 non-fast-forward / Everything up-to-date | 解：每次 push 前必须先 `git fetch origin` 看是否落后；若「main 落后 1」→ `git pull origin main`（自动合并成 merge commit，通常无冲突）再 push。这就是 Gatekeeper 模式每次上传先 pull 再 push 的原因 |
| 25 | **月度分析 vs 管理报表改同一个字段名 = 容易误改**：部门归并逻辑用户要求"只改管理报表后端"，但 MonthlyAnalysis 字段名和管理报表有复用（如 department 聚合逻辑），很容易顺手一起改 | 改之前先做明确 scope 划分：MonthlyAnalysis 改动先写下来确认不在 scope，改完立刻 `git diff src/pages/MonthlyAnalysis/index.tsx` 看是不是空白，有改动就 `git restore`；不要等 PR review 才发现 |
| 26 | **TRAE 子进程网络和你本机交互式窗口不是一条链路**：TRAE RunCommand 的 PowerShell 到 GitHub 443 总是 21s 超时，但你自己开的交互式 PowerShell 秒推成功——这是 TRAE 网络隔离/沙箱限制，不是代码/代理问题 | 把 TRAE 当「本地 git 操作 / 代码修改工具」，把「真正连 GitHub push」这个动作永远交给你自己开的交互式窗口（或双击 push-deploy.bat），不要再反复在 TRAE 里重试 push（21s×N=纯浪费时间） |
| 27 | **跨功能对话开发容易出现「前后端字段名没对齐」**：供应商对账页面在 reconciliation 对话改、后端接口在仓库对话改，两边没走 PR 联调 → 上线后前端空字段 | 跨模块改动（尤其是新模块调用已有 API）必须在 PR 描述里明确写「该 API 返回哪些字段、别名是什么」，Gatekeeper 合入时核对前后端字段名一致，不能光看"两边都改完了"就合 |

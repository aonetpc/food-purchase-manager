## 二、易错点 & 必须牢记的细节（重点回顾）

### ⚠️ 易错点1：后端 items-batch 的价格回填优先级

[checkup-templates.js PUT /:id/items-batch](file:///workspace/backend/routes/checkup-templates.js#L687-L731)

```js
const nameSnap = it.item_name_snapshot && String(it.item_name_snapshot).trim()
  ? it.item_name_snapshot : (ci.name || null);
const priceSnap = it.item_price != null ? it.item_price : round2(ci.default_price || 0);
```

📌 **规则**：
- 如果前端传了 `item_price`（即使是 0），后端直接用，**不查项目库**
- 只有 `item_price == null` 时，才会 LEFT JOIN 项目库回填 `default_price`

📌 **结论**：只要前端生成 flatItems 时用了旧快照 `si.price_snapshot`，就绕过了项目库查询 — 所以必须在前端初始化和保存两处都强制查项目库最新价。

### ⚠️ 易错点2：克隆 role_plans 的继承陷阱

[checkup-templates.js POST /:id/clone](file:///workspace/backend/routes/checkup-templates.js#L564-L657)

📌 **老逻辑**：`srcPlans` 从源套餐读出来，`round2(p.original_total)` 原样写入
📌 **新逻辑**：全部清零，**不继承**

📌 **为什么不能继承**：
1. 克隆出来的套餐项目明细可能完全不是原模板的（被用户修改），original_total 必须按新项目重算
2. 继承后即使后端重算（items-batch 会重写），中间状态也会让前端在 WizardFinish 显示"僵尸旧价"
3. discount_rate 继承 85%，克隆后用户没改，新的 original_total 重算后 discount_price 会被 `original * 0.85` 自动打折，但用户以为是"未修改的新套餐，应该原价" — 清零避免这个歧义

### ⚠️ 易错点3：React Hooks 顺序（SharePage 历史 Bug）

所有 hooks（`useMemo` / `useCallback` / `useEffect` / `useState` / `useXxx`）必须放在**组件顶部，在任何条件 return 之前**。

📌 错误示例：
```tsx
if (!pkg) return <div>加载中</div>;  // ← 条件 return
const plan = useMemo(() => calc(), [pkg]);  // ← 条件 return 之后才调用 hook → 白屏
```

📌 正确示例（已修复）：
```tsx
const plan = useMemo(() => calc(), [pkg]);  // ← 先算 hook
if (!pkg) return <div>加载中</div>;         // ← 再 return
```

### ⚠️ 易错点4：server.js 路由注册顺序（分享链接历史 Bug）

`server.js` 中路由挂载顺序：
1. **先挂**免登录路由（如 `/api/booking/checkup-share/*`，在 `requireAuth` 中间件之前）
2. **再挂**需要登录的路由（`/api/booking/*` 统一 `requireAuth`）

如果先挂 `/api/booking` requireAuth，再挂 `/api/booking/checkup-share`，**客户打开分享链接会被 requireAuth 拦截并跳登录页**。

📌 检查方式：读 `server.js`，搜索 `/api/booking/checkup-share` 是否在 `requireAuth(app, [])` 之前。

### ⚠️ 易错点5：字段名不匹配（品牌配置历史 Bug）

前端：`{ phone, address }` → 后端：`{ company_phone, company_address }`。

📌 正确做法（后端兼容两种字段名）：
```js
const company_phone = body.company_phone ?? body.phone ?? '';
```

📌 教训：前端字段名短，后端字段名完整带前缀时，**后端必须兼容短名**，不要让前端改（容易漏改，且前端传短名直觉更自然）。

## 三、关键决策记录

### 决策 1：分享流程走「先预览后分享」单按钮 + 文字三步提示

- **选择**：删除误导的「微信分享指引」弹窗，主按钮直接打开客户视角新标签页，下方用文字三步描述操作
- **原因**：
  - 直接在内部操作页分享会暴露销售折扣编辑等功能（极不安全）
  - 「预览客户视角」次按钮 + 「微信分享指引」主按钮的主次关系**相反**，用户直觉点主按钮
  - 弹窗指引只能在打开的瞬间看一眼，用户点完就忘；下方常驻文字提示，每次点按钮前都能看到
  - 客户视角页面本身是匿名访问的 H5，没有登录态限制，适合微信分享

### 决策 2：克隆套餐 role_plans 清零（不继承原模板价格）

- **选择**：克隆时 `original_total=0, discount_price=0, discount_rate=100`
- **原因**：
  1. 克隆后用户大概率会修改项目，原模板价格毫无意义
  2. 继承会在中间状态显示"僵尸价格"，用户困惑为什么改了项目价格没变
  3. 折扣率继承会导致重算后打折，但用户以为是"新套餐原价" — 100% 兜底语义清晰
  4. 后续 `items-batch` 一定会重算，清零是安全的初始化

### 决策 3：前端两处都强制查项目库最新价（初始化 + 保存）

- **选择**：`loadAll` 初始化 selected 和 `onSaveAndNext` 生成 flatItems 两处都按 `item_id` 从 `items[]` 查 `default_price/insurance_price/name`
- **原因**：
  1. 后端 items-batch 的回填优先级规则是「前端传了就用前端的，不传才查库」——如果只改初始化不改保存，保存时旧快照还是会被传给后端
  2. 两处都查，冗余但保险；保存时再次查库还能覆盖用户在 WizardItems 页停留期间项目库被管理员修改的极端情况
  3. 即使后端回填逻辑未来改动（比如改成严格模式），前端传最新价也不会出错

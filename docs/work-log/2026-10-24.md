## 三、关键决策记录

### 3.1 软取消终态（cancelled）而非物理删除

数据保留可追溯（取消人/时间/原因留痕），看板置灰展示，统计口径排除；admin 的物理删除功能保留并存，两不冲突。

### 3.2 已取消订单默认显示但置灰

用户决策：各营运部门需要在看板上看到「这笔单取消了」的事实（而非消失造成误解），通过灰色 + 删除线 + 角标区分；但所有统计口径（monthly-pax 后端三处 SQL、前端 stats/dayOrderCount/BizRow 项数）必须排除，否则数字失真。

### 3.3 取消权限走 RBAC 权限码而非角色硬编码

新增 `action:booking:cancel` 权限（button 类型），默认仅绑 admin，管理员可在角色管理页分配给预订员；与既有 `action:booking:approve` 等按钮权限同体系，服务端用 `req.user.permissionCodes` 校验。

### 3.4 迁移编号冲突修复用「改文件名」而非「改迁移框架」

migrate.js 的数字前缀 ID 规则已被 120+ 个历史迁移依赖，改成全文件名作 ID 会让 `schema_migrations` 历史记录全部不兼容，风险远大于收益；重命名新文件是唯一安全动作。

## 五、踩坑教训

1. **建迁移文件前必须列出 migrations 目录全部最新编号，不能只看相邻号**（ref：feat/218→219，2026-10-24）：只确认「最新分支号是 217」就取迁移号 120，没注意到 feat/216 已占用 120 且已随上轮部署入库。`migrate.js` 以数字前缀作 `schema_migrations.id` 主键，撞号后新迁移被静默跳过——**跳过不报错**，表现为「功能代码已上线但字段/权限不存在」，排查方向极易先怀疑部署失败。固定动作：建迁移文件前 `Get-ChildItem backend/migrations` 列尾部编号 + 确认主键唯一。

2. **迁移被跳过的症状是「部署成功但功能表现为未部署」，且报错点不在迁移处**（ref：feat/219，2026-10-24）：权限配置页看不到权限（权限行没插）是表象，真正的运行时爆炸点在管理员点「取消订单」时 500 `Unknown column 'cancelled_by'`。凡「部署后新功能缺失」先查 `schema_migrations` 是否有对应记录，再查字段/权限是否落库，两步即可定位。

3. **迁移框架的「幂等跳过」机制会把编号冲突变成静默失败**（ref：feat/219，2026-10-24）：`pending = files.filter(f => !executedIds.has(getMigrationId(f)))` 对撞号文件直接跳过，无警告。涉及多人/多分支并行开发时，迁移号占用应随分支号一起在建分支时确认。

4. **新增终态状态要先盘点全部统计口径再动手**（ref：feat/218，2026-10-24）：cancelled 加入后共排查出 4 处会误计已取消订单的口径（后端 monthly-pax 三处 SQL、前端 stats、dayOrderCount、BizRow 项数），全部同步排除；与既有「新状态盘点分散耦合点」规则一致，但统计口径（过滤排除方向）与流转白名单（准入方向）是两个清单，都要过一遍。

5. **软取消与物理删除并存时，群通知的链接策略不同**（ref：feat/218，2026-10-24）：cancel 通知保留 H5 链接（订单还在，可追溯），与既有「delete 类型不加链接」规则不冲突——链接有效性取决于订单是否还能查到，不取决于状态名。

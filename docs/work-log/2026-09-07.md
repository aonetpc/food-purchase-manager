## 一、批量入库匹配优化（fix/128）

### 1.1 背景

用户反馈"全自动免疫检测系统用底物液-安"被自动匹配到物资库已有物品，但实际物资库并没有该物品。根因是 [BatchInboundModal/index.tsx](file:///f:/OA/src/components/BatchInboundModal/index.tsx) `parseLine` 的本地匹配用了"包含关系"自动匹配，导致粘贴名和物品名任一方包含另一方就自动 `matched`。

### 1.2 修复1：本地匹配仅精确相等自动使用（3fee894）

[BatchInboundModal/index.tsx#L202-L208](file:///f:/OA/src/components/BatchInboundModal/index.tsx#L202) 本地匹配从三级包含关系改为仅精确相等：

```tsx
// 修改前：精确相等 / 物品名包含粘贴名 / 粘贴名包含物品名
const matchedItem = allItems.find((it) => {
  const itNorm = normalize(it.name);
  return itNorm === normName || itNorm.includes(normName) || normName.includes(itNorm);
});

// 修改后：仅精确相等
const matchedItem = allItems.find((it) => normalize(it.name) === normName);
```

### 1.3 修复2：相似度候选显示匹配度百分比（e442a22）

新增工具函数 `normalizeStr` / `levenshtein` / `similarityScore`（[L66-L102](file:///f:/OA/src/components/BatchInboundModal/index.tsx#L66)）：

- `levenshtein`：编辑距离动态规划算法，O(m*n)
- `similarityScore`：归一化到 0-100 的相似度分数，100 表示完全相同

`SearchableItemSelect` 组件增强（[L104-L186](file:///f:/OA/src/components/BatchInboundModal/index.tsx#L104)）：
- 候选计算相似度分数 → 按分数**降序排列** → 取前 50 条
- 每条候选显示百分比，颜色分级：
  - ≥80% 绿色
  - 50-79% 橙色
  - <50% 灰色

### 1.4 修复后的匹配流程

| 步骤 | 条件 | 结果 |
|------|------|------|
| 1. 本地精确相等 | normalize(name) === normalize(pastedName) | 自动 `matched` |
| 2. 后端精确查询 | `name = ?` | 自动 `matched` |
| 3. 后端相似度查询 | LIKE 包含 | `item_similar`，等用户人工选择 |
| 4. 无候选 | - | `item_missing`，手动新增或映射 |

## 四、入库加权平均单价（fix/131 + fix/132）

### 4.1 现象

房务仓库"儿童泳裤"导入2次：
- 第1次入库：2条 × ¥19.90
- 第2次入库：12条 × ¥24.90

库存数量正确（14条），但参考单价显示 ¥19.90（第1次的价），库存价值 ¥278.60（14×19.90）。第2次的 ¥24.90 完全没反映到参考单价。

### 4.2 根因

所有入库路径都只更新 `inventory.quantity`，从不更新 `warehouse_items.reference_price`：

| 入库途径 | 文件 | 问题 |
|---------|------|------|
| 批量入库 | [stock-movements.js#L200](file:///f:/OA/backend/routes/stock-movements.js#L200) | ❌ 未更新 reference_price |
| 手动入库 | [stock-movements.js#L130](file:///f:/OA/backend/routes/stock-movements.js#L130) | ❌ 未更新 reference_price |
| 采购入库 | [warehouse-purchases.js#L2545](file:///f:/OA/backend/routes/warehouse-purchases.js#L2545) | ❌ 未更新 reference_price |
| 扫码领料入库 | [scan-requisition.js#L178](file:///f:/OA/backend/routes/scan-requisition.js#L178) | ❌ 未更新 reference_price |

### 4.3 修复

**统一加权平均公式**：

```
weightedPrice = (oldQty × oldPrice + newQty × newPrice) / (oldQty + newQty)
```

保留 4 位小数，边界处理：
- oldQty ≤ 0 或 oldPrice ≤ 0 → 直接用新单价
- 首次入库 → 直接用新单价
- 未提供单价 → 不更新 reference_price

**fix/131（6ec30d8）**：批量入库 + 手动入库
- [stock-movements.js#L200-L228](file:///f:/OA/backend/routes/stock-movements.js#L200) 批量入库
- [stock-movements.js#L130-L156](file:///f:/OA/backend/routes/stock-movements.js#L130) 手动入库

**fix/132（97812a8）**：采购入库 + 扫码领料入库
- [warehouse-purchases.js#L2540-L2575](file:///f:/OA/backend/routes/warehouse-purchases.js#L2540) 采购入库
- [scan-requisition.js#L173-L208](file:///f:/OA/backend/routes/scan-requisition.js#L173) 扫码领料入库

### 4.4 修复后效果

儿童泳裤第2次入库后：
- reference_price = (2×19.90 + 12×24.90) / 14 = **24.1857**
- 库存价值 = 14 × 24.1857 = ¥338.60（而非错误的 ¥278.60）

## 七、报销管理页批量刷新审批状态（fix/133）

### 7.1 背景

### 7.2 现状分析

| 维度 | 情况 |
|---|---|
| 单据表 | `purchase_confirmations` |
| 单条刷新接口 | `POST /purchase-confirmations/:id/refresh-status` |
| 批量刷新接口 | 无 |
| 前端按钮 | 每条报销单展开后有"刷新状态"按钮（[L509-L517](file:///f:/OA/src/pages/ReimbursementManager/index.tsx#L509)），页面顶部无批量刷新按钮 |

### 7.3 方案选择

| 方案 | 做法 | 优缺点 |
|---|---|---|
| A 前端串行调单条 | 循环 `await api.post(...refresh-status)` | 不改后端但 N 个 HTTP 请求慢 |
| **B 后端新增批量接口** ✅ | 新增 `/batch-refresh-status` | 一次 HTTP 请求，后端串行避免限流 |
| C 前端并行调单条 | `Promise.allSettled` | 不改后端但可能触发企微 45009 限流 |

3. **浮点数值计算和显示需使用 cleanFloat 工具函数**（ref：fix/129）：保留4位小数并去除末尾无意义的0
4. **盘点通知收件人必须从 warehouse_users 关联表查询**（ref：fix/130）：避免 warehouses.manager_userid 旧字段未同步
5. **所有入库路径必须按加权平均法更新物资参考单价**（ref：fix/131, fix/132）：覆盖批量/手动/采购/扫码四个入口
6. **fromBackend 递归 snakeToCamel 会转换 extra 内部键名**（ref：fix/132）：读取 `extra` 内嵌套对象的 snake_case 字段时必须兼容 camelCase（如 `female_married ?? femaleMarried`），否则条件判断失败走兜底逻辑
7. **体检套餐 items-batch 需按 (item_id, role) 去重**（ref：fix/131）：前端可把同一项目同时放入公共区和角色区，autoCorrectItemRole 纠正后撞唯一键
8. **企微 API 批量调用必须串行避免 45009 限流**（ref：fix/133, fix/134）：并行调用企微审批 API 会触发频率限制错误 45009，必须 `for...of` 串行调用
9. **Express 路由顺序敏感**（ref：fix/133, fix/134）：`/batch-refresh-status` 必须注册在 `/:id/refresh-status` **之前**，否则 `batch-refresh-status` 被当成 `:id` 匹配
10. **批量刷新应过滤终态单据减少无效调用**（ref：fix/133, fix/134）：只查 `reimbursement_status IN ('pending','processing')` 或非终态的单据，避免对已 approved/rejected 的单据发起无效企微 API 调用
11. **确认弹窗不要用 window.confirm**（ref：fix/134）：体验差，应改用自定义 Modal（仿项目已有的 SendConfirmModal 模式），支持样式/loading/禁用关闭等
12. **仓库采购单据有 4 种 sp_no**（ref：fix/134）：批量刷新需按 `status` 自动选择刷新哪个 sp_no（approval_sp_no / prepay_sp_no / reimbursement_sp_no / monthly_payment_sp_no），不能一刀切
13. **企微配置只查一次复用给每条**（ref：fix/133, fix/134）：批量接口里 `getWecomConfig()` 在循环外调一次，避免 N 次 DB 查询

### 7. 模板逻辑重构：克隆模式

- **问题**：原模板逻辑是把原订单 `UPDATE is_template=1`，导致原订单从列表消失
- **用户需求**：模板应该和正常订单同时存在，模板只是为了快速下单用
- **修复方案**：
  - `set-template`：原 `UPDATE` 改为 `INSERT` 克隆一条新记录（order_no 以 `TPL` 前缀，`is_template=1`），原订单保持 `is_template=0` 不变
  - `unset-template`：原 `UPDATE` 改为 `DELETE` 删除模板副本（不影响来源订单）
  - 历史数据自动修复：`ensureFixLegacyTemplates` 函数，检测 `is_template=1 AND order_no NOT LIKE 'TPL%'` 的旧订单，恢复为普通订单 + 克隆同名模板
- **涉及文件**：
  - [booking-board.js](file:///workspace/backend/routes/booking-board.js) — cloneOrderAsTemplate / set-template / unset-template / ensureFixLegacyTemplates
  - [index.tsx](file:///workspace/src/pages/BookingBoard/index.tsx) — 弹窗文案 + 模板卡片 UI
- **状态**：✅ 已部署

#### 8b. 用此模板创建报错 `Column 'customer_name' cannot be null`

- **根因（双重）**：
  1. `pool.query` 返回 `[rows, fields]`，原代码 `const [tpl] = await pool.query(...)` 取到的是 `rows[]` 数组，`tpl.customer_name` 是 `undefined` → INSERT NOT NULL 报错
  2. apply 接口 INSERT `booking_items` 字段名与迁移 064 不一致（用了不存在的 `adult_count/child_count/qty/package_code`）
- **修复**：
  - 解构修复：`const [tplRows] = conn.query(...); tpl = tplRows[0];`
  - 兜底值：`customer_name` 为空时用 `模板名-客户`
  - items 字段对齐：INSERT 使用迁移 064 的正确列 `item_type/date/start_time/end_time/pax/extra/amount/sort_order`
  - 连接统一：整个接口所有查询改为 `conn.query` 走同一事务
- **涉及文件**：
  - [booking-board.js](file:///workspace/backend/routes/booking-board.js#L1371-L1454) — apply 接口重构

## 三、关键决策记录

### 决策 1：体检套餐项目存储方式 — 关联+快照混合模式

- **选择**：`booking_package_items` 关联 `booking_checkup_items` 主表 + `item_name_snapshot` 名称快照
- **原因**：
  - 纯直接存储：改主表不影响套餐 ✅，但无法统一管理项目 ❌
  - 纯关联引用：可统一管理 ✅，但主表改名/删除会影响历史套餐 ❌
  - 混合模式：可统一管理 + 名称快照不受主表改名影响 ✅

### 决策 2：模板改为克隆模式

- **选择**：set-template 克隆新记录，原订单保持不变
- **原因**：用户需求是"模板和正常订单同时存在"，原 UPDATE 模式会让原订单从列表消失，不符合业务逻辑

### 决策 3：角色统计使用 UNION DISTINCT

- **选择**：合并 `user_roles` 和 `users.role_id` 两处来源后再分组计数
- **原因**：避免同一用户在多角色表和旧单角色字段都有记录时被双重计数

## 一、问题背景

管理员用户「钱育健」拥有多角色（admin / purchaser / sales / temp_auditor），但在预订调度看板看不到「业务配置」按钮，且添加新角色后历史权限功能出现故障，重新登录多次无效。

### 1.1 数据库现状

- `user_roles` 表：钱育健有 4 个角色记录（admin、purchaser、sales、temp_auditor）
- `users.role_id`：指向 purchaser 角色（sort_order=5，非最小）
- `users.role`：字符串字段，旧版数据残留

### 1.2 角色 sort_order

| 角色 | sort_order |
|------|-----------|
| admin | 1 |
| booker | 2 |
| finance | 3 |
| boss | 4 |
| purchaser | 5 |
| sales | 6 |
| viewer | 7 |
| ... | ... |
| temp_auditor | 11 |

## 二、根因分析（三层叠加）

### 2.1 第一层：req.user.roles 缺失

后端 `requireAuth` 中间件只设置 `req.user.role`（取 sort_order 最小的单角色），没有设置 `req.user.roles` 数组。前端和后端所有基于 `req.user.role === 'admin'` 的判断在多角色场景下全部失效。

### 2.2 第二层：旧版 users.role 字段被忽略

`getUserRoleCodes` / `requireAuth` / `requireRole` / `getUserPermissions` / `getUserMergedPermissions` / `isManagerUser` 只查 `user_roles` 表 + `users.role_id`，完全忽略了 `users.role` 字符串字段。钱育健的 admin 角色在某些数据状态下只存在于 `users.role` 字段。

### 2.3 第三层：MySQL DISTINCT + ORDER BY 冲突（ERROR 3065）

角色查询 SQL 为：
```sql
SELECT DISTINCT r.code
FROM (...) t
JOIN roles r ON r.id = t.role_id
ORDER BY r.sort_order ASC
```

MySQL 严格模式下，`ORDER BY r.sort_order` 引用的字段不在 `SELECT DISTINCT` 列表中，触发 ERROR 3065，主查询抛错走 catch 分支，只返回 `users.role_id` 对应的 purchaser 单角色。

## 六、部署踩坑：手动 nohup 进程导致 CI/CD restart 失败

### 6.1 现象

fix/multi-role-sql-distinct-orderby 合并 main 后，CI/CD 流水线 `restart` 阶段失败：
```
Error: listen EADDRINUSE: address already in use 127.0.0.1:3001
```

### 6.2 根因

排查过程中为了快速验证修复，在服务器上用 `nohup node server.js &` 手动启动了一个进程（绕过 systemd）。该进程占用了 3001 端口，导致 CI/CD 通过 `systemctl restart food-purchase-backend` 启动新进程时端口冲突。

### 6.3 修复

```bash
# 杀掉手动启动的进程（占用 3001 端口）
sudo fuser -k 3001/tcp
# 重新运行 CI/CD restart job 或 systemctl restart
sudo systemctl restart food-purchase-backend
```

## 十、关键经验

### 10.1 MySQL DISTINCT + ORDER BY 兼容性

MySQL 严格模式（`ONLY_FULL_GROUP_BY`）下，`SELECT DISTINCT col1 ... ORDER BY col2` 要求 `col2` 必须在 SELECT 列表中，否则报 ERROR 3065。

**修复模式**：
```sql
-- 错误
SELECT DISTINCT r.code FROM roles r ORDER BY r.sort_order ASC
-- 正确
SELECT DISTINCT r.code, r.sort_order FROM roles r ORDER BY r.sort_order ASC
```

### 10.2 catch 静默吞错导致排查困难

角色查询函数的 catch 分支只做降级返回，不打日志。本次 SQL 错误被静默吞掉，接口正常返回但数据错误，导致排查方向走偏（先怀疑数据、再怀疑部署、最后才发现是 SQL 错误）。

**改进方向**：所有 catch 降级分支必须 `console.error` 记录原始错误，便于日志排查。

### 10.3 部署验证必须用实际接口数据

修复后不能只看代码正确，必须：
1. 重启服务（确认新代码加载）
2. 用浏览器控制台实际调用接口验证返回数据
3. 确认 UI 行为符合预期

本次修复经历了三轮（fix/201 → fix/202 → fix/sql），每轮都是通过实际调用 `/auth/me` 才发现问题未解决。

### 10.4 手动启动进程必须用 systemd 管理

服务器上 Node.js 服务由 systemd（`food-purchase-backend`）管理。排查时用 `nohup node server.js &` 手动启动进程会绕过 systemd，导致：
- CI/CD restart 阶段因端口占用失败（EADDRINUSE）
- 手动进程不会被 systemd 监控，崩溃后不会自动重启

**规则**：服务器上重启服务统一用 `sudo systemctl restart food-purchase-backend`，不要用 nohup 手动启动。

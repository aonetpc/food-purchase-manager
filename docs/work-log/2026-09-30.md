## 一、问题现象

新用户扫码进入外请人员打卡 H5 登录页后，点击"微信登录"按钮无反应，页面显示红色错误"未登录，请先登录"。

## 二、根因分析

### 2.1 调用链

```
新用户扫码 → Login.tsx 页面加载 → initLogin()
  → handleWechatAuth() → 无 code 参数 → getWechatAuthUrl()
    → api.get('/wecom/config')  // 试图获取 wx_app_id
      → 后端 GET /api/wecom/config 路由有 requireAuth + requireRole('admin')
        → 用户无 OA token → 401 { error: '未登录，请先登录' }
  → catch → setError + setLoading(false) → 页面显示登录按钮 + 错误
```

用户点"微信登录" → 再次调用 `getWechatAuthUrl()` → 同样 401 → 按钮 onClick 无 try-catch → 错误被静默吞掉 → 按钮看似无反应。

### 2.2 根因

**fix/190-security-hardening** 安全加固给 `/wecom/config` 加了 `requireAuth` + `requireRole('admin')` 守卫。该守卫本身正确（`/config` 返回完整配置含密钥脱敏、银行账号等敏感字段），但 Login.tsx 之前错误地依赖此接口获取 `wx_app_id`，安全加固后新外请用户（无 OA 系统 token）无法访问。

| 问题 | 位置 |
|------|------|
| 根因 | `/wecom/config` 需要 admin 权限，但获取 `wx_app_id` 是公开操作 |
| 次因 | 按钮 onClick 无 try-catch，错误被静默吞掉 |

## 三、修复方案（commit `15842a3`，2 files，+18/-3）

### 3.1 后端：新增公开端点

**文件**：[backend/routes/wecom.js](file:///f:/OA/backend/routes/wecom.js#L551-L560)（+11 行）

在 `/config` 路由前插入新路由，无需认证，只返回微信公众号 AppID（OAuth 流程公开值，跳转 URL 中本就暴露给用户，非密钥）：

```js
router.get('/wx-app-id', async (req, res) => {
  try {
    const [rows] = await pool.query('SELECT app_id FROM wechat_config WHERE id = 1');
    res.json({ wx_app_id: rows.length > 0 ? rows[0].app_id : '' });
  } catch (err) {
    console.error('[/wx-app-id] 获取微信公众号 AppID 失败:', err);
    res.status(500).json({ error: '获取微信配置失败' });
  }
});
```

### 3.2 前端：改用公开端点 + 加错误处理

**文件**：[src/pages/temp/Login.tsx](file:///f:/OA/src/pages/temp/Login.tsx#L113)（+10/-3 行）

1. `getWechatAuthUrl()` 中 `api.get('/wecom/config')` → `api.get('/wecom/wx-app-id')`
2. "微信登录"按钮 onClick 加 try-catch，错误显示给用户而非静默吞掉

## 四、安全影响

- `/wecom/config` 的 admin 守卫**保持不变**，不回退安全加固
- 新端点只暴露 `wechat_config.app_id` 一个字段，该值在 OAuth 跳转 URL 中本就对用户可见，不引入新风险
- 符合 Lessons Learned：敏感操作接口加 requireAuth，仅将公开字段拆分为独立端点

## 五、验证

- TypeScript：Login.tsx 改动简单，无类型问题

## 七、fix/195：销售确认阶段订单被修改后保持 sales_confirming 状态

### 7.1 背景

销售员收到企微通知卡片「订单待确认（已修改）」，提示"订单已于 2026-09-29 11:55:19 被修改，请重新确认"。但点进去页面显示状态是"待审核"（`reviewing`），销售员看不到自己的确认按钮。

### 7.2 根因

[booking-board.js](file:///f:/OA/backend/routes/booking-board.js#L2524-L2533) 订单编辑接口中，`sales_confirming` 状态被修改时，后端错误地把 `status` 改成了 `reviewing`，同时清空了销售确认痕迹。

```js
// 修改前（BUG）
if (originalStatus === 'sales_confirming') {
  await conn.query(`UPDATE booking_orders SET
      status = 'reviewing',          // ← BUG：应该保持 sales_confirming
      sales_confirmed_at = NULL,
      sales_confirmed_by = NULL,
      sales_confirmed_by_name = NULL,
      sales_confirmed_signature = NULL
    WHERE id = ?`, [orderId]);
}
```

**流程矛盾**：通知逻辑按 `originalStatus = sales_confirming` 发了"请重新确认"卡片给销售员，但状态已被改成 `reviewing`，销售员无权操作（fix/193 之后更明显，操作区被角色守卫隐藏了）。

### 7.3 修复（commit `9da5a4b`，1 file，+2/-2）

```js
// 修改后
if (originalStatus === 'sales_confirming') {
  await conn.query(`UPDATE booking_orders SET
      sales_confirmed_at = NULL,
      sales_confirmed_by = NULL,
      sales_confirmed_by_name = NULL,
      sales_confirmed_signature = NULL
    WHERE id = ?`, [orderId]);
  // 注意：不改变 status，保持 sales_confirming
}
```

### 7.4 效果

| 场景 | 修改前 | 修改后 |
|---|---|---|
| sales_confirming 被修改 | status → reviewing，销售员点进去看不到确认按钮 | status 保持 sales_confirming，销售员能看到确认按钮 |

## 八、feat/196：预订订单审批流程历史记录功能

### 8.1 背景

审批流程展示只根据订单**当前字段**算出 4 个固定步骤（预订员提交 → 销售员确认 → 审核员审核 → 订单完成），如果订单经历过"驳回→修改→重新提交→再确认"等循环，这些中间步骤全部丢失，只看到最终状态。

### 8.2 实现（commit `b63a453`，4 files，+162/-4）

#### 8.2.1 迁移 SQL：[117_booking_order_flow_logs.sql](file:///f:/OA/backend/migrations/117_booking_order_flow_logs.sql)

新建 `booking_order_flow_logs` 表，字段：id / order_id / action / action_label / operator_id / operator_name / remark / signature / created_at

#### 8.2.2 后端 [booking-board.js](file:///f:/OA/backend/routes/booking-board.js)

- 新增 `writeFlowLog(conn, orderId, action, actionLabel, user, extra)` 辅助函数（失败不阻断主流程）
- 新增 `GET /orders/:id/flow-logs` 接口（表不存在时降级返回空数组，兼容迁移未跑窗口）
- 在 7 个流转操作中追加写入：

| 操作 | action | action_label | remark | signature |
|---|---|---|---|---|
| 提交 | submit | 预订员提交 | — | — |
| 销售员确认 | sales_confirm | 销售员确认 | — | 签字 |
| 驳回 | reject | 驳回（审核员/销售员） | 驳回原因 | — |
| 修改 | edit | 修改 | 修改摘要 JSON | — |
| 审核通过 | approve | 审核通过 | — | 签字 |
| 标记完成 | complete | 标记完成 | — | 签字 |
| 撤回 | withdraw | 撤回 | — | — |

#### 8.2.3 前端 [api.ts](file:///f:/OA/src/lib/api.ts)

- 新增 `FlowLog` 接口
- 新增 `bookingApi.getFlowLogs(orderId)` 方法

#### 8.2.4 前端 [BookingConfirm/index.tsx](file:///f:/OA/src/pages/BookingConfirm/index.tsx)

- 加载订单时同步获取 flowLogs
- `buildFlowSteps` 重构为两条路径：
  - **有 flowLogs**：从日志构建完整动态步骤列表（含多次驳回/修改/重新提交循环），末尾追加"当前待操作"步骤
  - **无 flowLogs**：回退到原有 4 步逻辑（兼容迁移未跑或老订单）

### 8.3 效果示例

```
✅ 预订员提交    石佩    2026-09-14 14:54
✅ 销售员确认    严文斌  2026-09-14 15:30  [签字]
🔴 驳回          审核员  2026-09-15 10:00  驳回原因：金额有误
✅ 修改          石佩    2026-09-15 10:30  修改项：金额、用餐人数
✅ 预订员提交    石佩    2026-09-15 11:00
✅ 销售员确认    严文斌  2026-09-15 11:30  [签字]
🔄 审核员审核（待操作）   （当前步骤）
```

### 8.4 部署注意

- 需在部署时执行迁移 `117_booking_order_flow_logs.sql`（GitHub Actions migrate 阶段自动跑）
- 老订单无 flow_logs 记录，审批流程展示与之前一致（回退兼容）
- 新操作从此开始记录，后续流转会逐步积累历史

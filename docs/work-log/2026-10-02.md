## 一、问题分析

### 1.1 现象一：点击「生成月结账单」后，待月结采购单消失

用户操作「生成月结账单」后，「待月结采购单」列表变空，采购单找不到。

**根因**：

[reconciliation.js](file:///f:/OA/backend/routes/reconciliation.js) 的 `POST /reconciliation/generate` 接口做了两件事：
1. 在 `monthly_statements` 表创建 `status='pending'` 的账单
2. 把关联采购单的 `monthly_statement_id` 设为账单 ID

而「待月结采购单」列表查询条件是 `monthly_statement_id IS NULL`，所以被归并进账单的采购单就从列表里消失了。

**附带发现**：生成账单时未排除已发起付款的采购单（缺少 `AND monthly_payment_sp_no IS NULL`），导致已付款的采购单也被错误归并进 pending 账单。

### 1.2 现象二：已申请付款，审批通过后记录找不到

用户在「待月结采购单」勾选 → 发起付款申请 → 进入「月结付款审批中」→ 点击「刷新审批状态」→ 审批通过后记录消失。

**根因**：

审批通过后后端执行 `UPDATE warehouse_purchases SET monthly_paid_at = NOW() WHERE monthly_payment_sp_no = ?`。而「月结付款审批中」列表查询条件是 `monthly_paid_at IS NULL`，所以已付款的记录被排除，但页面上**没有「已付款」列表来展示这些记录**，造成"蒸发"假象。

### 1.3 统计卡数字不准

「待月结池」统计卡只判断 `monthly_statement_id IS NULL`，不判断 `monthly_pending`，导致审批中的采购单（`monthly_pending = 0`）被误计入。

## 二、数据恢复操作

### 2.1 诊断

通过 SQL 查明 pending 账单关联的 16 张采购单状态：
- 6 张已发起付款且已付款完成（`monthly_pending = 0`，`monthly_paid_at` 有值）
- 10 张未发起付款（`monthly_pending = 1`，`monthly_payment_sp_no IS NULL`）

### 2.2 恢复 SQL（事务包裹）

```sql
START TRANSACTION;

-- 1. 清空 16 张采购单的 monthly_statement_id
UPDATE warehouse_purchases
SET monthly_statement_id = NULL
WHERE monthly_statement_id IN (
  SELECT id FROM monthly_statements
  WHERE status = 'pending' AND purchase_type = 'monthly'
);

-- 2. 删除 9 张 pending 月结账单
DELETE FROM monthly_statements
WHERE status = 'pending' AND purchase_type = 'monthly';

-- 3. 校验
SELECT COUNT(*) AS remaining_pending FROM monthly_statements
WHERE status = 'pending' AND purchase_type = 'monthly';  -- 应为 0

COMMIT;
```

### 2.3 恢复结果

- 16 张采购单 `monthly_statement_id` 重置为 NULL
- 9 张误生成的 pending 账单删除
- 10 张未付款采购单回到「待月结采购单」列表
- 6 张已付款采购单保持已付款状态不变

## 六、关键决策记录

| 决策 | 原因 |
|------|------|
| 只恢复 `pending` 状态的月结账单，不动 confirmed/approved/paid | 后者有实际业务意义，避免误删已处理数据 |
| 恢复操作只改 `monthly_statement_id`，不碰付款相关字段 | 已付款采购单的付款状态不受影响 |
| 去掉「生成月结账单」流程而非修复 | 该流程与用户实际的"直接付款"流程重叠且更繁琐，还容易导致数据混乱 |
| 月份筛选按 `sp_no` 提取申请月份 | 审批单号格式为 `YYYYMMDD+序号`，能准确反映付款申请时间 |
| 付款时间取审批单实际 `sptime` | 比 `NOW()` 更准确，避免"刷新时间≠实际付款时间"的偏差 |
| 保留月结账单后端接口 | 兼容历史数据，避免破坏其他依赖，前端只是隐藏入口 |

## 九、fix/200：修复 Create.tsx React.useRef 未定义导致白屏

## 十、关键经验补充

### 10.1 React Hooks 导入规范（本次踩坑）

文件顶部如果是 `import { useState, useRef, ... } from 'react'`（只导入命名导出），代码中**不能**使用 `React.useRef`、`React.useState` 等形式。必须：
- 要么改为 `import React, { useRef } from 'react'`（导入默认 React）
- 要么直接用 `useRef`（推荐，与文件其他部分风格一致）

排查信号：页面白屏 + 控制台 `React is not defined` → 检查最近改动中是否有 `React.xxx` 用法，而文件 import 未引入默认 React。

### 10.2 功能开发与 Bug 修复必须分离

本次 feat/199 引入了 React.useRef bug，但因为功能分支未立即部署，问题在用户验收时才发现。正确做法：
- 功能分支提交后，**必须在本地启动 dev server 实际操作一遍**核心入口（如新建订单），不能只靠 `npm run build` 通过
- build 通过只说明类型和语法正确，不代表运行时无错误

### 10.3 PC/H5 两端展示逻辑必须同步

菜单展示逻辑在 PC 端（index.tsx DetailModal）和 H5 端（BookingConfirm MealDetails）都实现了，且都包含：折叠展示、多图横滚、模板名标签、历史备注兼容。避免出现一端有菜单一端没有的情况。

## 五、出错的地方（实时记录）

### 🔴 出错1：技术债 #10 代码审计挖出"会议厅+房型配置"的 fromBackend 系统性 Bug

📌 **为什么之前没发现**：
1. 会议厅价格虽然显示 ¥0，但在 `calcMeetingAmount` 中 `row.half_price || 0` = 0 后会**fallback 到 FALLBACK_HALLS 常量**的硬编码价格（四季厅 2000/3500），实际上大部分时间靠 fallback 常量兜底，功能表面上是"工作的"
2. 房型表格的 sort_order = undefined 在 `Number(undefined)` → `NaN` 渲染，可能显示成空白或奇怪的字符，用户以为是操作问题
3. 房型 pricing_mode 字段昨天才新增，部署后用户还没来得及反馈就被今天审计发现了

📌 **排查过程（有效方法论）**：
```
日志注意事项 #1 → 说 api.ts 中 meetingHalls/salesUsers 还在走 fromBackend，可能有陷阱
           ↓
全局 grep meetingHalls 的渲染，找 half_price / halfPrice 的用法
           ↓
发现渲染代码清一色用 snake_case（BizConfigModal、Create.tsx、utils.ts）
           ↓
反查 api.ts listMeetingHalls 等 CRUD 函数 → 全部走了 fromBackend
           ↓
结论：所有从后端读取的数据字段名会被 fromBackend 改成 camelCase，与 snake_case 渲染不匹配 → 真实 Bug
```

📌 **教训（必须加入长期记忆）**：
1. **`fromBackend` 会把 snake_case 全改成 camelCase** —— 这不是"可选格式美化"，而是**破坏性地改变对象键名**
2. **如果渲染代码用 snake_case 字段（如 half_price、sort_order、pricing_mode），那么 API 层绝对不能走 fromBackend**
3. **配置类 CRUD 的 4 个 API 必须统一处理策略**：不能 getConfig 一个策略、listXxx 另一个策略、createXxx 第三个策略——今天就是 roomTypes 同时存在"3 种不同策略"导致隐患
4. **代码审计要完整**：昨天只修了 getConfig 一个入口，漏了 list/create/update 三个独立入口。今天的系统性检查一次性覆盖了所有入口。

📌 **修正后的统一策略（写入文件头注释规范，供后续新增配置参考）**：
```
API 层字段命名策略：
- 配置类（roomTypes / meetingHalls / wellnessTypes / mealTypes / checkupItems）
  → 全部保持后端 snake_case，不走 fromBackend
  原因：渲染代码、类型定义（types.ts）与后端表格列都是 snake_case
- 订单 / 用户 / 权限类（orders / salesUsers 等）
  → 允许走 fromBackend 转 camelCase
  原因：前端 state / props 都是 camelCase（如 salesPersonId、contactName）
```

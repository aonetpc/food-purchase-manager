## 五、出错的地方（实时记录）

### 🔴 出错1：技术债 #10 代码审计挖出"会议厅+房型配置"的 fromBackend 系统性 Bug

📌 **为什么之前没发现**：
1. 会议厅价格虽然显示 ¥0，但在 `calcMeetingAmount` 中 `row.half_price || 0` = 0 后会**fallback 到 FALLBACK_HALLS 常量**的硬编码价格（四季厅 2000/3500），实际上大部分时间靠 fallback 常量兜底，功能表面上是"工作的"
2. 房型表格的 sort_order = undefined 在 `Number(undefined)` → `NaN` 渲染，可能显示成空白或奇怪的字符，用户以为是操作问题
3. 房型 pricing_mode 字段昨天才新增，部署后用户还没来得及反馈就被今天审计发现了

📌 **排查过程（有效方法论）**：
```
日志注意事项 #1 → 说 api.ts 中 meetingHalls/salesUsers 还在走 fromBackend，可能有陷阱
           ↓
全局 grep meetingHalls 的渲染，找 half_price / halfPrice 的用法
           ↓
发现渲染代码清一色用 snake_case（BizConfigModal、Create.tsx、utils.ts）
           ↓
反查 api.ts listMeetingHalls 等 CRUD 函数 → 全部走了 fromBackend
           ↓
结论：所有从后端读取的数据字段名会被 fromBackend 改成 camelCase，与 snake_case 渲染不匹配 → 真实 Bug
```

📌 **教训（必须加入长期记忆）**：
1. **`fromBackend` 会把 snake_case 全改成 camelCase** —— 这不是"可选格式美化"，而是**破坏性地改变对象键名**
2. **如果渲染代码用 snake_case 字段（如 half_price、sort_order、pricing_mode），那么 API 层绝对不能走 fromBackend**
3. **配置类 CRUD 的 4 个 API 必须统一处理策略**：不能 getConfig 一个策略、listXxx 另一个策略、createXxx 第三个策略——今天就是 roomTypes 同时存在"3 种不同策略"导致隐患
4. **代码审计要完整**：昨天只修了 getConfig 一个入口，漏了 list/create/update 三个独立入口。今天的系统性检查一次性覆盖了所有入口。

📌 **修正后的统一策略（写入文件头注释规范，供后续新增配置参考）**：
```
API 层字段命名策略：
- 配置类（roomTypes / meetingHalls / wellnessTypes / mealTypes / checkupItems）
  → 全部保持后端 snake_case，不走 fromBackend
  原因：渲染代码、类型定义（types.ts）与后端表格列都是 snake_case
- 订单 / 用户 / 权限类（orders / salesUsers 等）
  → 允许走 fromBackend 转 camelCase
  原因：前端 state / props 都是 camelCase（如 salesPersonId、contactName）
```

### 🔴 出错2：住宿早餐天数偏移 —— "入住当天就送了早餐"（少算了退房当天那顿，多算了入住当天）

**用户现象描述**：订单 8/18 入住 8/20 退房 2 晚 → 早餐出现在 8/18 和 8/19（2天2顿），正确应该是 8/19（第二天早）和 8/20（退房早）这 2 顿。

**根因**：`deriveBreakfastSessions` 住宿循环写的是：
```ts
for (let i = 0; i < nights; i++) { add(dateCheckIn + i天) } // ❌ 从第0天=入住当天开始
```
应改为：
```ts
for (let i = 1; i <= nights; i++) { add(dateCheckIn + i天) } // ✅ 从第1天=入住次日 → 第n天=退房日早
```

**为什么会错**：A+ 第一版写"for i from 0"是沿用了「入住几天就几顿」的直觉写法，但酒店行业标准是**送第二天早餐 + 退房当天早餐（nights=nights顿）**，差了 1 天的偏移。这是**业务规则错误**不是代码错误——以后做"住宿派生餐饮"的需求必须先画时间线，不能靠直觉写循环。

**后端同步修复**：`booking-board.js deriveBreakfastItems` 的住宿分支犯了同样的 `i=0` 错误，一并修改为 `i=1`。

📌 **教训**：
1. 餐饮派生需求先画时间线（横轴日期、纵轴业务日期），再写循环
2. 同构的前后端逻辑（如早餐派生）修改时前端后端必须**同时改**，不得只改一个

---

### 🔴 出错3：早餐人数按「rooms × beds」而非实际入住 pax —— 虚高

**用户现象**：按间 10 间 × 2 床，实际只住了 10 人（每间 1 人），系统却派生了 20 份早餐。

**根因**：A+ 第一版按间模式早餐写的是 `rooms × getBedsPerRoom()`，这是"理想化满床推算"，忽略了实际订房时**用户会手动填 pax（不满床）**。

**修复**：无论 pricing_mode，早餐优先取用户实际填写的 `pax`，pax 缺失（旧订单）时才兜底 rooms×beds。

📌 **教训**：用户手动输入的值（pax）优先级永远高于配置推算值（rooms×beds），推算值只能做 fallback 兜底，不能做正常逻辑。

### 🔴 出错4：早餐人数体检+住宿相加 —— "同一批人被算两次"（严重）

**用户现象描述**：订单有体检 20 人 + 住宿 20 人 → 早餐变成 40 人。用户说"住宿的这 20 人就是体检的那 20 人，早餐就 20 人"。

**根因**：A+ 第一版早餐汇总逻辑：
```ts
pax: (v.checkupPax || 0) + (v.lodgingPax || 0)  // ❌ 叠加
```

**正确逻辑**：同一团队体检=住宿的人是同一批，取最大值 `Math.max(checkupPax, lodgingPax)`。

📌 **教训**：
1. "派生"和"叠加"必须严格区分：同一人多身份覆盖场景一律取 **max**，多组不同人加总场景才用 **sum**
2. 修完这个，团队用餐（午餐/晚餐）也要检查同样的问题，很可能午餐/晚餐也存在相同叠加 Bug（今日 CheckList）

### 🔴 出错5：配套餐卡片长名优化第一版「手机 1 列」被用户否决

**用户现象描述**：我之前提的方案 D 写的是「手机竖屏 1 列」，用户截图后明确要求"手机竖屏最少 2 列，字体可以缩，文字要显示全面"。

**为什么错**：我做 UI 优化时**擅自判断了屏幕密度和内容密度**，加了 `sm:` 断点才变 2 列——实际上用户的主力设备就是手机竖屏，且体检项目多，2 列才能保证同屏信息密度足够。不是"为了好看"优化，是"为了用户使用场景"优化，这一点搞反了。

📌 **教训**：做 UI 改版前**先问用户的典型使用设备**（手机竖屏？平板横屏？PC？），不要根据自己的"移动端 UI 美观最佳实践"来做，要根据用户的**实际工作场景**来。

### 🔴 出错6：配套餐长名第二版「前4字 font-extrabold + 后半稍细」造成整页字重不统一

**用户现象描述**：截图里有的项目名（短名 4 字内）整字超粗（如「血常规」「血沉」全在前 4 字内 = 超粗），长名前半超粗后半又浅，视觉很不协调。

**为什么错**：我错误地引入了「首字分段式加粗」来解决"HPV16 vs HPV23 vs 全套分不清"的命名识别问题——其实**分段式加粗是排版大忌**，只适用于标题/标签，不适合列表项。用户看到的是"字体有的粗有的正常"，会直觉这是 Bug 而不是设计。

**正确解法**：识别度问题靠**hover 气泡或 tooltip**解决，列表项字体必须**统一字重/颜色**，颜色只留三种状态（选中/未选/已排除）。

📌 **教训**：列表类视图中的文字样式只能有「状态差」，不能有「片段差」。一段文字内不能出现 2 个字重或 2 个颜色（高亮搜索词除外）。
